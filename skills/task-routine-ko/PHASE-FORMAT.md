# PHASE-FORMAT — Phase 1–4 가 화면에 내는 것

> Phase 1 진입 시 1회 읽는다. **게이트**(무엇이 일어나면 안 되는가)는 `SKILL.md` 에 있고, 이 파일은 **출력의 형태**다. 형태를 베끼되 예시 데이터는 베끼지 않는다.

아래 예시는 전부 같은 실행이다 — Node/TypeScript API 저장소, 로컬 `TODO.md`, 미완료 4건. 한 번의 실행, 네 개의 Phase 라서 형태가 서로 이어진다. 여기서 벗어나는 블록은 둘이고 둘 다 나오는 자리에 그렇게 적었다: 이 실행이 도달하지 않는 Phase 4 의 브레이크 발동, 그리고 원격 소스가 필요한 pending 완료 질문.

---

## Phase 1 — 작업 해석

**유효 설정을 맨 먼저 출력한다** — 무엇을 해석하기도 전에. 다이얼, 상한, 소스, 검증 명령을 각각 출처를 달아서, 그리고 무시된 것이 있으면 함께. 그다음 소스에 대해 셋을 보고한다: 어디를 봤는가, 무엇을 찾았는가, 얼마나 오래됐는가. 추천을 떠받치는 것은 신선도다.

선행 분석이란 **이 프로젝트 결정 로그에서 `source_ref` 가 같은 가장 최근 실행**이고, 그 정렬·그룹핑은 그 실행의 체크포인트에서 온다. 따로 쓸 분석 파일도, 낡아갈 파일도, 실수로 repo 에 커밋될 파일도 없다.

| 같은 소스에 대한 선행 실행의 나이 | 추천 |
|---|---|
| 24시간 이내 | 그 정렬·그룹핑 재사용 |
| 24시간 ~ 7일 | 재사용하되 노후 표시 |
| 7일 초과 | 다시 도출 |
| 30일 초과 | 무시 — 선행 실행이 없는 것으로 진행 |

```
설정    레벨 auto (--auto) · max_tasks 5 (전역) · 소스 TODO.md (프로젝트)
        검증 "npm test" (프로젝트 config, 이 repo 에 승인됨)
무시    프로젝트 config 의 autonomy.level — 다이얼은 repo 가 정할 것이 아니다

소스    TODO.md (로컬 마크다운) · 미완료 4건
선행    실행 20260816T0611, TODO.md — 3시간 전 → 정렬 재사용 (24h 이내)

  1  [ ] 목록 API 에 정렬 파라미터 추가
  2  [ ] 목록 응답 캐싱
  3  [ ] /admin/* 에 관리자 role 요구
  4  [ ] 캐시 히트율 리포트
```

테스트를 별도 경로로 두지 않는 repo — Rust `#[cfg(test)]`, in-source Vitest — 는 여기 한 줄이 더 붙는다. `테스트   in-source; 이 repo 에서는 Step 3 주장 검사를 돌리지 않음` 이고, 그 말을 하는 자리는 여기뿐이다(`SKILL.md` §Step 3).

`무시` 줄은 무시된 것이 있을 때만 나온다. `선행` 줄도 마찬가지다 — 어떤 소스에 대한 프로젝트의 첫 실행에는 선행 실행이 없고, 그건 "없음" 이라는 줄이 아니라 줄의 부재로 보고된다. 이 repo 에서의 첫 실행 — 또는 승인 이후 명령 텍스트가 바뀐 경우 — 검증 줄은 보고가 아니라 질문이 된다:

```
⛔ 이 검증 명령은 당신이 아니라 repo 가 준 것입니다

   node scripts/verify.js          (.claude/task-routine.json)
   구현 루프 이터레이션마다 1회, 단위당 최대 3회 실행됩니다. TDD 를 택한 항목은 행동 검사마다 더 실행할 수 있습니다.

   이 repo 에 승인 / 다른 명령 입력 / 중단
```

선행 분석이 없으면 추천 줄만 빠진 같은 형태다. 그리고 **항목이 0건**이면 찾아본 경로를 출력하고 거기서 멈춘다. 빈 소스는 보고할 결과이지 작업을 지어내라는 신호가 아니다.

```
소스    TODO.md (로컬 마크다운) · 미완료 0건
탐색    ./TODO.md · ./docs/TODO.md · .claude/task-routine.json → source.path

미완료 항목 없음. 실행할 것이 없다.
```

## Phase 2 — 정렬

결과만이 아니라 간선을 보인다. 사용자가 확인할 수 없는 재정렬은 사용자가 고칠 수도 없다.

```
정렬    의존성 기준 (간선 2개)

  1 → 2   캐시 키에 정렬 파라미터가 들어가야 하므로 정렬이 먼저
  2 → 4   캐시가 있어야 잴 것이 생긴다
  3       독립

결과    1, 3, 2, 4      (소스 순서는 1, 2, 3, 4)
```

소스 순서 유지도 정당한 결과이며 `결과    변경 없음` 으로 같은 형태를 쓴다.

## Phase 3 — 그룹핑과 실행자 선택

### 그룹핑 판정

| 두 항목의 관계 | 판정 |
|---|---|
| B가 A의 산출물을 소비 | **순차** |
| 서로 다른 파일 | **병렬** |
| 같은 파일 다른 영역 | 병렬 가능 — 단 diff 가 겹칠 것 같으면 순서를 준다 |
| 같은 파일 같은 영역 | **순차**, 예외 없음 |

### 실행자 사다리 — 가능한 가장 높은 단이 이긴다

| 단 | 요건 | 격리 |
|---|---|---|
| 설정된 멀티플렉서 | `execution.executor` 설정, 그 `command` 를 찾음, `session_env` 가 비어 있지 않음 | 자체 pane / worktree |
| 네이티브 서브에이전트 | 항상 가능 | 항목당 `git worktree` 1개 |
| 순차 | — | 없음 |

**어느 단에 내려앉았는지, 그리고 왜 위쪽이 불가능했는지 말한다.** 조용히 병렬에서 순차로 강등된 실행은 애초에 병렬이 아니었던 실행과 화면상 구분되지 않는다.

**그룹 편성으로 TDD 를 잃는 항목을 말한다.** worker 는 테스트를 돌릴 수 없으므로(`references/execution.md` 의 계약 6) worker 가 맡은 항목은 TDD 를 고를 수 없다. 그런 항목 중 변경 형태가 TDD 를 제안하거나 추천하는 것마다 — `BUILD-LOOP.md` §2a 의 표, 아직 안 읽었으면 지금 읽는다 — 그룹 아래에 한 줄을 단다: 선택지를 빼앗는 것은 그룹 편성이고, Step 2 에서는 말하기에 늦다.

```
그룹

  G1  (병렬)        1  정렬 파라미터 추가      src/api/list.ts
                    3  관리자 role 요구        src/api/admin.ts, src/auth/guard.ts
  G2  (G1 이후)     2  목록 응답 캐싱          src/api/list.ts, src/cache/*
  G3  (G2 이후)     4  캐시 히트율 리포트      src/cache/metrics.ts

  ⚠️ 1과 2가 src/api/list.ts 를 함께 건드린다 — 영역이 달라 병렬 대신 순서를 줬다
  ⚠️ 1과 3은 테스트를 돌릴 수 없는 worker 로 간다 — TDD 가 선택지에서 빠진다(BUILD-LOOP §2a)

실행자  네이티브 서브에이전트 + git worktree
        config 에 execution.executor 없음 → 3단 중 2단
```

## Phase 4 — 요약

### 결과 표

| 컬럼 | 내용 |
|---|---|
| `#` / 항목 | 번호와 제목 |
| 상태 | ✅ 완료 · ⚠️ 상한 넘겨 진행 · ⏭️ 건너뜀 · ❓ 끝났지만 이 실행이 뒷받침할 수 없는 것을 커밋함 — 테스트 전략과 실제로 쓴 것이 어긋나거나(주장한 테스트가 없거나 `none` 이라 해 놓고 동작을 썼거나), dirty 경로 정지를 지나쳐 커밋이 2c 가 검증한 트리가 아니거나. **⚠️ 가 연속 실패 카운터를 올리고, ⏭️ 는 이 실행이 이미 예산을 쓴 항목일 때만 올리며**, ✅ 가 지우고, ❓ 는 둘 다 하지 않는다 (`SKILL.md`) |
| 테스트 | 고른 전략이 아니라 **실제로 쓴** 전략 |
| 재검증 | 실패한 재검증 횟수 · 상한 도달 시 `(cap)` · 머지된 그룹의 공용 카운터면 `(group)` |
| 커밋 | 짧은 해시, 커밋이 없으면 `—` |

```
Task Routine — TODO.md · 4항목 · 레벨 auto · 18분

| # | 항목                  | 상태 | 테스트   | 재검증  | 커밋    |
|---|-----------------------|------|----------|---------|---------|
| 1 | 정렬 파라미터 추가     | ✅   | unit+int | 1 (group) | a1b2c3d |
| 3 | 관리자 role 요구       | ✅   | unit+int | 1 (group) | c3d4e5f |
| 2 | 목록 응답 캐싱         | ⚠️   | unit+int | 3 (cap)   | e4f5g6h |
| 4 | 캐시 히트율 리포트     | ❓   | none     | 0         | f7g8h9i |

커밋 4개 · 변경 파일 14개
⚠️ 항목 2 는 상한에서 지적 1건을 남긴 채 확정됐다 — "LRU 축출에 테스트 없음" — 수동 확인 필요
❓ 항목 4 는 2a 에서 "unit" 을 고르고 테스트 경로를 하나도 쓰지 않았다 (src/cache/metrics.ts 뿐).
   커밋됐고 초록이지만, 이 단위가 낸 테스트 중 그것을 받치는 것은 없다.
연속 실패 항목 2 이후 2 중 1 — 항목 4 의 ❓ 는 올리지도 지우지도 않았다
TODO.md — 완료 표시 4건, 미커밋
```

테스트 주장 미달로 나온 `❓` 행의 `테스트` 칸이 `none` 인 것은 그 컬럼이 **실제로 쓴** 것을 담기 때문이다. *고른* 전략은 아래 줄에 적히고, 모순이 읽히는 자리는 거기뿐이다. `none` 을 정당하게 고른 단위도 여기 `none` 을 찍고 ✅ 를 유지한다 — 두 행은 무엇을 주장했느냐에서 갈리지 칸이 보여 주는 것에서 갈리지 않으며, 그래서 줄이 보고하는 것은 주장이다.

항목 1 과 3 은 머지된 한 그룹이라 재검증 카운트를 **하나** 공유해 표시한다, 각자 하나가 아니다. 실패 카운터 줄은 그 카운터가 움직였을 때만 나온다 — 매 실행 `2 중 0` 을 찍는 것은 소음이고, 움직였는데 안 찍는 것은 실행이 중단에 얼마나 가까웠는지를 감춘다.

브레이크가 실제로 발동하면 실행은 그 자리에서 멈추고 무엇이 발동시켰는지 이름을 댄다 — 이건 `references/autonomy.md` 에 추적표로 실린 여섯 항목 실행이고, 위 실행이 아니다:

```
⛔ 연속 실패 브레이크 — 두 항목 연속 ⚠️ 또는 ⏭️ (항목 5 ⚠️ 상한 · 항목 6 ⏭️)
⏭️ 항목 7, 8 시도 안 함

   체크포인트 기록. --resume 은 아직 pending 인 첫 단위, 항목 7 부터 카운터를 복원해 이어간다.
   항목 6 은 시도했다가 건너뛴 것이고, 건너뜀은 끝난 상태이지 재시도 대상이 아니다.
```

### 결정 감사 — 완전 수동이 아니었다면 필수

네 컬럼이고 중요한 것은 네 번째다: **결과가 그 선택을 뒷받침했는가?** 결과 없는 결정 표는 감사가 아니라 로그다.

```
사용자 대신 내린 결정 (레벨 auto)

| 항목 | 단계      | 선택        | 근거                        | 결과          |
|------|-----------|-------------|-----------------------------|---------------|
| 1    | S1-design | 루프 생략   | 단일 파일, 새 인터페이스 없음 | clean         |
| 1    | S2-test   | unit+int    | 저장소를 건드리는 엔드포인트  | 재검증 1 (G1) |
| 3    | S2-test   | unit+int    | 권한 규칙, worker 엔 TDD 불가 | 재검증 1 (G1) |
| 3    | S1-design | 2라운드     | 새 인증 표면                 | blocking 1 수정 |
| 2    | S2-test   | unit+int    | 캐시 계층 = 통합 표면        | 재검증 3 ⚠️   |
| 4    | S2-test   | unit        | 순수 함수, 경계 없음         | 주장 미달 ❓   |
| 2    | S2-review | 로컬 diff   | PR 없음, gh 있으나 브랜치 미푸시 | 지적 1     |

자동이 아니라 물어본 것: 항목 3 security 표면(승인), 항목 2 상한 도달(현 상태로 확정)
```

마지막 줄은 장식이 아니다. **사람 앞에서 멈춘 것**을 자동으로 지나간 것 옆에 함께 보여야, 읽는 사람이 "위험한 게 없었다" 와 "가드가 한 번도 안 울렸다" 를 구분할 수 있다.

### pending 완료 — 이 실행이 쓰지 못한 전부

Step 3 이후 쥐고 있던 것을 전부 나열하고 실행당 한 번만 묻는다. 이 블록은 원격 소스가 필요하므로 위 실행의 `TODO.md` 원본이 아니라 GitHub 이슈 변형이다:

```
pending 완료 — GitHub issue #142, 4건
  ☑ 1  정렬 파라미터 추가
  ☑ 3  관리자 role 요구
  ☑ 2  목록 응답 캐싱
  ☑ 4  캐시 히트율 리포트

트래커 쓰기는 절대 자동이 아니다. 4건 모두 반영할까?
```

거부되거나 실패한 것은 체크포인트에 `pending` 으로 남고 pending 으로 보고된다 — 절대 완료로 보고하지 않는다.
