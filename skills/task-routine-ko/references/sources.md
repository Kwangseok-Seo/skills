# sources — 작업 소스 어댑터

> 작업 해석(Phase 1) 시 읽는다. 출력 형태는 `PHASE-FORMAT.md` 에 있고, 이 파일은 계약과 기본 제공 구현 둘이다.

## 계약

어댑터는 셋에 답한다. 스킬의 나머지 전부는 이 셋만 보고 쓰였다.

| 멤버 | 반환 | 쓰는 곳 |
|---|---|---|
| `locality` | `"local"` 또는 `"remote"` | **`S3-done` 의 등급을 결정한다** — 장식이 아니다 |
| `list()` | 순서 있는 `[{ id, title, done, ref }]` | Phase 1 |
| `complete(id)` | 반영, 또는 보류 | Step 3 |

- `id` — **실행을 넘어 안정적이어야 한다.** 체크포인트·결정 로그·`--resume` 이 전부 이걸 키로 쓴다.
- `title` — 한 줄, 무슨 작업인지.
- `done` — 이미 끝난 것. 다시 돌리지 않고 걸러낸다.
- `ref` — 커밋 메시지에 들어갈 것, 없으면 `null`.

### locality 가 등급을 결정한다 — 이게 비대칭의 전부다

```
S3-done, 등급이 정책이 아니라 데이터인 결정:

locality == "local"    완료 표시 = 파일 편집     → auto-eligible, 즉시 반영
locality == "remote"   완료 표시 = 트래커 쓰기   → manual-only, pending 기록 후 Phase 4 에서 일괄
```

이걸 *GitHub 에 관한 규칙*이 아니라 *소스의 속성*으로 쓴 것이, 세 번째 어댑터가 왔을 때도 맞게 만드는 이유다. 새 어댑터는 자기 locality 를 선언하기만 하면 Step 3 를 아무도 고치지 않고 올바른 동작을 물려받는다.

### 안정적인 id, 그리고 그것이 움직일 때

파일 기반 소스에서는 **줄 번호를 쓰지 않는다**: 2번 항목을 체크하면 파일이 다시 쓰이고 그 아래 id 가 전부 밀린다. id 는 항목 텍스트에서 끌어낸다(제목의 짧은 슬러그나 해시). 제목이 ASCII 가 아니면 슬러그는 제목과 아무 관계 없는 문자열이 되므로 **해시를 쓴다** — 알아볼 수 없는 슬러그보다 정직하다.

이건 실패 하나를 더 작은 실패로 바꾼 것이다 — 작업 문구를 고치면 id 가 바뀌어 옛 id 가 사라지고 새 id 가 생긴다. **조용히 해결하지 말고 보고한다:**

```
pending id 가 소스에 없다: h-9f2a1c4e
가장 가까운 항목: "목록 응답 캐싱 (TTL 포함)"  (새 id: h-3b7d05a1)
같은 작업인가, 이름만 바뀐 건가?
```

유사도로 조용히 매칭하면 엉뚱한 작업을 완료로 찍고, 조용히 버리면 끝낸 작업의 기록을 잃는다. 묻는 비용은 프롬프트 하나다.

## `markdown` — 기본 어댑터

```json
{ "adapter": "markdown", "path": "TODO.md" }
```

- `locality`: `local`
- 작업은 중첩 깊이와 무관하게 GFM 체크박스다: `- [ ]` 미완료, `- [x]` 완료.
- 작업 아래 중첩된 항목은 그 작업의 **상세**이지 별도 작업이 아니다. `title` 맥락으로 함께 넘기되 목록으로 펼치지 않는다.
- `ref`: `null` — 로컬 파일에는 인용할 외부 참조가 없다.
- `complete(id)`: **파일을 다시 읽고 나서** 그 한 줄의 `[ ]` 를 `[x]` 로 바꾼다. 그 외에는 건드리지 않는다 — 파일을 재포맷하면 한 글자 변경이 아무도 리뷰할 수 없는 diff 가 되고, `list()` 가 Phase 1 부터 쥐고 있던 사본을 그대로 써 내리면 실행이 도는 동안 사용자가 체크리스트에 더한 줄이 지워진다. 그 줄들은 커밋된 적이 없으므로 아무것도 되돌려 주지 못한다.

```markdown
## 스프린트

- [x] 페이지네이션 헬퍼 추출
- [ ] 목록 API 에 정렬 파라미터 추가
  - `sort=field:asc|desc` 를 받는다
  - 모르는 필드는 400 으로 거부
- [ ] 목록 응답 캐싱
```

→ 미완료 2건. 들여쓴 두 줄은 첫 항목의 상세다.

## `github` — 이슈 task list

```json
{ "adapter": "github", "repo": "owner/name", "issue": 142, "token_env": "GITHUB_TOKEN" }
```

- `locality`: `remote`
- 프로브가 찾은 `gh` 가 필요하다. 없으면 말하고 소스를 묻는 쪽으로 폴백한다 — 사용자가 지정하지 않은 로컬 파일로 **절대** 조용히 갈아타지 않는다.
- `list()`: 이슈 본문을 읽어 같은 체크박스 문법으로 파싱.
- id: 위와 똑같이 텍스트에서 끌어낸다 — 이슈 본문 속 체크박스는 자기 id 가 없고, 이슈 번호가 가리키는 것은 이슈이지 항목이 아니다.
- `ref`: `#142` (현재 repo 와 다르면 `owner/name#142`).
- `complete(id)`: 이슈 본문을 편집한다. 이건 트래커 쓰기라 `pending` 으로 쥐고 있다가 Phase 4 에서 질문 한 번으로 일괄 반영된다.

읽기는 `gh issue view <n> --json body,title`, 쓰기는 `gh issue edit <n> --body-file -`. 체크박스 문자만 바꾼다 — 본문을 포매터에 통과시키면 사람이 적어 둔 것이 사라진다.

실제 이슈에 대고, 정확히 저 두 형태로 실측: CRLF 줄끝, 트레일링 공백 hard break, 탭 들여쓰기, 비ASCII 텍스트, 이모지, HTML 주석, 공백뿐인 줄, 마지막 개행 없음을 담은 본문이 **바이트 단위로 동일하게** 돌아왔다 — 204 바이트가 나갔다 돌아왔고 CR 3개가 그대로였으며 — 차이는 체크박스 문자 하나뿐이었다. 전송 계층은 아무것도 정규화하지 않고, 그래서 위 규칙이 강제 가능하다: 여기서 왕복이 무언가를 잃었다면 그것을 잃은 것은 GitHub 이 아니라 그 사이의 코드다.

## 어댑터 추가하기

답할 것은 이 셋뿐이다.

1. **`locality` 는 무엇인가?** 애매하면 안전한 쪽으로 틀려라 — `remote` 는 실행당 프롬프트 하나가 비용이고, `local` 을 잘못 선언하면 무인으로 트래커에 쓴다.
2. **id 는 어디서 오고, 편집을 견디나?** 소스가 진짜 id(이슈 키, row id)를 주면 그걸 쓰고 더 고민하지 않는다. 아니면 텍스트에서 끌어내고 위의 rename 보고를 받아들인다.
3. **`ref` 는 무엇인가?** `git log` 를 읽는 사람이 그 작업을 다시 찾으려면 필요한 것.

명세만 있고 구현하지 않은 어댑터가 둘 있다 — `jira`(이슈 키 + 체크리스트)와 `url`(가져온 마크다운 문서). 위 셋에 답하면 어렵지 않지만, 둘 다 공개 저장소에서 실제 인스턴스에 대고 검증할 수 없어 넣지 않았다. 아무도 시험할 수 없는 어댑터는 아무도 안 쓴 어댑터보다 나쁘다.
