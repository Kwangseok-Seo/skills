# execution — 실행자 계약과 폴백 사다리

> Phase 3 가 만든 **그룹 중 하나라도 항목을 2개 이상 담을 때** 읽는다 — 그룹 개수가 아니라 그것이 한 repo 에 동시 워커를 넣는 조건이다. 순차 실행에는 이 파일이 필요 없다.

## 계약

실행자를 자처하려면 여섯을 모두 만족해야 한다. 특정 도구가 아니라 **계약**을 보고 쓴다 — 그래야 사이클을 다시 쓰지 않고 사다리가 강등될 수 있다.

1. **격리.** 동시에 도는 두 항목이 작업 디렉터리를 공유하지 않는다.
2. **쓰기 권한.** worker 가 파일을 만들고 고칠 수 있다. 아래 실패 양상 참조.
3. **결과 회수.** 각 worker 의 변경 파일 목록과 요약을 종료 후 가져올 수 있다.
4. **종료 보장.** 모든 worker 는 끝나거나 타임아웃으로 선언된다. 실행을 매달아 둘 수 있는 worker 는 없다. 마감은 `execution.timeout_minutes`(기본 20)이지 실행마다 지어내는 숫자가 아니다.
5. **정리는 가역이거나 질문한다.** §정리 참조.
6. **격리 강제.** 실행자가 worker 를 읽기와 파일 쓰기로 제한할 수 있어야 한다. 브리프는 worker 가 쥐고 있는 도구를 제약하지 못한다: 의존성 설치를 돌려보내라고 시켜도 셸을 가진 worker 는 그냥 `npm i` 를 돌리고, 그중 diff 에 닿는 것은 락파일 델타뿐이며 `postinstall` 은 이미 실행된 뒤다. **worker 의 도구를 제한하지 못하는 실행자는 이 계약을 만족하지 않는다** — 한 단 내려가고 그 사실을 말한다.

검증·리뷰·커밋은 **실행자의 일이 아니다.** 머지 뒤에 그룹 단위로, 메인 스레드에서 순차 실행된다 — 예산 하나, 리뷰어 하나, 커밋 컨벤션 하나.

**테스트 전략도 실행자의 것이 아니고, 방향이 반대다: `S2-test` 는 항목마다, 메인 스레드에서, 그 항목의 worker 를 띄우기 *전에* 고르고 브리프에 담는다.** 그것은 이 항목을 무엇이 검증할지를 말하는 것이라, 머지 뒤에 고르면 worker 들의 테스트 — 또는 그 부재 — 를 이미 화면에 놓고 고르는 것이 된다. 그러면 Step 3 은 주장을 그 주장을 만들어 낸 바로 그것에 대고 검사하게 되고, 어떤 단위도 거기서 미달이 될 수 없다. 미리 정하면 그것은 worker 에게 지키라고 요구하는 약속이 된다.

## 사다리

| 단 | 요건 | 격리 | 쓸 때 |
|---|---|---|---|
| 1 · 설정된 멀티플렉서 | `execution.executor` 가 설정돼 있고, 그 `command` 가 `PATH` 에 있고, **그리고** `session_env` 가 설정돼 있고 비어 있지 않음 | 자체 pane·worktree | 사용자가 세팅해 두고 보고 있을 때 |
| 2 · 네이티브 서브에이전트 | `git` 외 아무것도 | 항목당 `git worktree` 1개 | 1단이 불가능한 모든 경우의 기본값 |
| 3 · 순차 | 없음 | 없음 | 그룹이 하나거나 worktree 가 현실적이지 않은 repo |

**한 단 내려가는 것은 보고이지 가정이 아니다.** 1단에서 2단으로 조용히 떨어진 실행은 애초에 멀티플렉서가 없던 실행과 구분되지 않고, 무슨 일이 있었는지에 대한 사용자의 모형이 조용히 틀어진다:

```
실행자   2단 — 네이티브 서브에이전트 + git worktree
         멀티플렉서는 설정돼 있으나(herdr) HERDR_ENV 미설정 → 살아 있는 세션이 아님
```

1단의 세부는 설정된 도구 쪽에 속한다. 이 스킬이 요구하는 것은 위 키(`references/setup.md`)와, 그 도구가 여섯 계약을 만족하는 것이다. **`execution.executor` 가 없으면 불가능해질 1단 자체가 없다**: "멀티플렉서 미설정" 이라는 보고는 없는 바이너리가 아니라 없는 키를 가리키고, 아무도 그것을 쓰지 않은 지금은 모든 실행이 그 상태다.

## 2단 — 네이티브 서브에이전트 + worktree

항목당 worktree 하나, worktree 당 서브에이전트 하나:

```bash
git worktree add -b tr/<task-id> ../<repo>-<task-id>
```

각 서브에이전트에 주는 것: 작업, Step 1 에서 확정된 plan, **위에서 그 항목에 대해 고른 `S2-test` 전략**, 자기 worktree 경로, 그리고 권한 — 하면 안 되는 것의 목록이 아니라 **해도 되는 것**으로 진술한다:

```
해도 됨   무엇이든 읽기 · 자기 worktree 경로 아래에서 파일 생성·수정
그 외      하지 않는다 — 요청으로 메인 스레드에 돌려보내고
           작업의 나머지를 계속한다
```

**허용 집합으로 쓰는 것이 요점이다.** worker 는 이번 실행에서 사람에게 닿는 통로가 없는 유일한 자리라 자기가 하는 어떤 것도 물어볼 수 없다. 그러니 네 가지를 금지한 브리프는 아무도 금지할 생각을 못 한 나머지 전부를 조용히 허용한 것이다 — 파일 삭제, 의존성 설치, 네트워크 호출, worktree 밖 쓰기. 네 hard stop 부류는 메인 스레드에 있고, 행위를 돌려보내는 것이 worker 가 거기에 닿는 유일한 길이다.

커밋, push, 브랜치 조작, 검증 명령 실행은 이 규칙에서 따라 나오지 규칙이 열거하는 것이 아니다 — 그 넷은 머지 이후 메인 스레드의 일이기도 하고, 커밋하는 worker 는 머지를 읽을 수 없게 만든다.

worker 는 계약의 회수분을 반환한다: 변경 파일, 요약, 그리고 하지 못한 것.

**머지 전에 각 worktree 를 커밋하는 것은 메인 스레드다.** worker 는 파일을 쓰고 멈춘다. 커밋이 하나도 없는 브랜치는 여전히 그룹 시작 커밋을 가리키므로 `git merge --no-ff` 는 `Already up to date` 를 찍고 exit 0 으로 아무것도 머지하지 않는다 — 가능한 가장 시끄러운 침묵이다. 그래서 돌아온 worker 마다, 그 worktree 안에서: 쓴 것을 스테이징하고, repo 컨벤션으로 커밋하고, 그다음 머지한다. 커밋이 메인 스레드에 남는 이유는 커밋이 위험해서가 아니라 메시지 컨벤션과 hard stop 이 거기 있기 때문이다.

**무엇을 썼는지는 두 번 읽고, 두 읽기가 일치해야 한다.** 여기서 `git add -A` 는 그 디렉터리에 있는 것을 전부 커밋한다 — worker 의 작업도, 빌드 산출물도, 캐시 디렉터리도, 아무도 gitignore 하지 않은 임시 파일도 똑같이. 그것은 `SKILL.md` 가 이 스킬의 다른 모든 커밋을 위해 한 절을 통째로 들여 세운 규율을, **사람이 가장 멀리 있는 바로 그 자리에서** 버리는 것이다. 그렇다고 worker 가 돌려준 목록만 믿으면 더 조용한 실패로 바꾸는 것일 뿐이다: 적게 보고한 worker 는 머지에서 작업을 잃고 아무것도 그 사실을 말하지 않는다.

그러니 둘을 대조한다 — 그룹 시작 커밋 기준으로 `SKILL.md` 가 대는 명령 두 개로 뜬 그 worktree 자신의 변경 집합과, 계약 3항이 이미 요구하고 있는 worker 의 변경 파일 목록. **일치 → 정확히 그것을 Step 3 이 커밋하는 방식으로 커밋한다**: `--only`, 되읽기, 인자 한계 형태 — 한 번 정의된 하나의 행위를 다른 디렉터리에서 수행하는 것. **불일치 → 멈추고 묻는다**, 양쪽을 다 이름으로 대고. worker 가 보고한 것 밖에 썼거나 쓰지 않은 것을 보고했거나 둘 중 하나이고, 어느 쪽도 짐작으로 머지할 일이 아니다. 비교는 **repo 상대 경로의 집합**으로, 먼저 정규화해서 한다: worker 가 내놓는 것은 산문이고, 절대 경로나 `./` 접두사나 다른 구분자는 무슨 일이 있었는지가 아니라 표기에 대한 불일치다. 표기로 멈추는 가드는 꺼진다.

```bash
git -C ../<repo>-<task-id> commit --only -m "<컨벤션>" -- <합의된 경로들>
git merge --no-ff tr/<task-id>
```

worker 가 돌아왔는데도 커밋할 것이 없는 브랜치는 깨끗한 결과가 아니라 아래의 read-only 실패다.

### 쓰기 권한은 조용한 실패다

read-only 로 뜬 worker 는 에러를 내지 않는다. 편집이 하나씩 거부되는데 성공을 보고한다 — 에이전트 안에서 보면 잘못된 게 없기 때문이다. 거부당했고, 넘어갔을 뿐이다. 그러면 실행은 빈 브랜치를 머지하고 하나도 바뀌지 않은 코드베이스를 검증한다.

**띄울 때 쓰기 능력을 확인하고, "변경 파일 없음" 을 깨끗함이 아니라 의심으로 취급한다.** plan 이 파일 셋을 지목했는데 worker 가 하나도 안 바꿨다면 아무것도 안 하는 데 성공한 게 아니라 무언가에 실패한 것이다.

## 머지

그룹을 의존성 순으로 하나씩, `--no-ff` 로 머지해 그룹 경계가 이력에 남게 한다. 충돌은 정지다 — 충돌 경로를 보고하고 묻는다: *직접 해소하고 계속 / 이 그룹 포기 / 실행 중단*. worker 간 충돌을 무인으로 해소하지 않는다. 두 worker 각자 일관된 plan 을 갖고 있었고, 그중 하나를 고르는 것이 바로 다이얼이 덮지 않는 판단이다.

**답마다 진행 중인 머지가 어떻게 되는지를 말한다. 어느 답도 그것을 기본값으로 처리해 주지 않는다:**

| 답 | 진행 중인 머지 |
|---|---|
| 직접 해소하고 계속 | 해소가 스테이지되고 `git merge --continue` 가 끝낼 때까지 남는다 — Step 3 의 `--only` 형태가 **아니다**. git 은 머지 중에 그것을 거부하고, 그 exit 는 `SKILL.md` 가 이미 갈라 놓은 128 중 하나다. 아직 끝낼 머지가 있는지는 가정하지 말고 git 에 묻는다: `git rev-parse -q --verify MERGE_HEAD` — 비어 있고 exit 1 이면 해소한 사람이 이미 커밋한 것이다. 스테이지가 안 됐으면 `--continue` 도 거부한다. 그리고 그건 인자를 받지 않으므로 유추로 붙이는 `--no-edit` 은 머지가 아니라 **129** 다 |
| 이 그룹 포기 | `git merge --abort`, **그 exit 를 읽는다** — 아래 참조 |
| 실행 중단 | 남는다. 그리고 보고가 그렇게 말한다: 돌려주는 것은 머지 도중인 repo 다 |

아무 말도 안 하는 것은 그대로 두는 것과 같지 않다. 충돌한 트리는 tracked 파일 안에 마커를 그대로 갖고 있어서 그 경로가 단위의 변경 집합에 남고 — 실측, `git diff --name-only --no-renames <그룹 시작 커밋>` 이 `UU` 경로를 나열한다 — 거기서 2c 와 hard stop 스캔과 다음 단위의 `dirty_at_start` 로 흘러간다.

**`git merge --abort` 는 거부될 수 있고, 거부하는 것 중 하나는 이 스킬이 만든다.** exit 가 0 이 아니면 포기는 일어나지 않았고 머지는 그대로 있다. 실측으로 분리해 확인: 인덱스의 intent-to-add 엔트리 — 변경 집합 계산이 요구하는 `git add -N` 에서 온다 — 는 `Entry '<경로>' not uptodate. Cannot merge.` 와 함께 **128** 로 나가고, 평범한 수정 파일과 untracked 파일은 둘 다 깨끗이 abort 된다. 그 엔트리가 **이 실행**이 만든 것이면 — 사용자의 것과 가르는 것은 `SKILL.md` 의 이른 untracked 읽기다 — 거기에 `git rm --cached` 를 하면 abort 가 되살아나고 파일은 untracked 로 디스크에 남는다. 그 밖의 원인은, 알고 보니 사용자의 것이었던 경우까지 포함해서: 상태를 보고하고 넘긴다. **`git reset --hard` 로 올라가지 않는다** — abort 를 막은 것이 무엇이든 커밋되지 않은 작업이고, 여기는 수리가 실패보다 비싼 유일한 경로다.

성공한 abort 는 두 브랜치가 여전히 갖고 있지 않은 것을 아무것도 destroy 하지 않는다. 머지를 다시 돌리면 그 충돌 트리가 재현되기 때문이고, 그래서 `autonomy.md` §2 의 복구가능성 시험이 이것을 — 포기라는 답이 이미 온 뒤에 — 두 번째 질문으로 만들지 않는다. **누군가 손으로 이미 시작한 해소는 예외다** — 그 편집은 어느 브랜치에도 없다 — 그러니 그것을 이름으로 대고 버리기 전에 확인한다.

그룹이 머지되면 그 그룹에 대해 Step 2 를 메인 스레드에서 **2c 부터** 돌린다 — 전략은 띄우기 전에 골랐고 구현은 방금 머지된 것이다 — 수리가 필요하면 다른 이터레이션과 똑같이 2b 로 재진입하고, 그다음 Step 3.

**hard stop 은 여기서 판정한다.** worker 는 물어볼 수 없으므로, 네 부류는 그 그룹의 변경 집합 — `SKILL.md` 가 고정한 그 집합이고, 그룹 자신의 시작 커밋에서 계산되며, 워킹 트리를 비우는 머지에도 살아남는다 — 에 대고 메인 스레드에서, 그 그룹의 커밋 전에 검사한다. worker 가 쓴 security 표면도 순차로 쓴 것과 똑같이 질문을 받는다, 사이클에서 조금 늦을 뿐이다. worker 가 돌려보낸 요청도 같은 자리에서 같은 부류를 적용해 답한다.

그룹은 변경 집합이 하나지만 **확정 plan 은 N개**다. 그래서 범위 시험은 그 **합집합**을 읽는다: 항목 1이 지운 파일을 항목 3의 plan 에 대고 물으면 거짓 정지가 나고, 아무 plan 에도 안 물으면 거짓 통과가 난다.

## 정리

worktree 제거는 파괴적 로컬 작업이라 hard stop 이다 — 예외 하나를, 도구가 바뀌어도 계속 맞도록 규칙으로 쓴다:

```
이번 실행이 만들었다  ∧  브랜치가 머지됐다  ∧  worktree 가 깨끗하다   → auto-eligible
그 외                                                                  → 질문
```

세 연언 전부이고, 열거가 빠뜨리는 것이 세 번째다. 커밋이 **하나도 없는** 브랜치는 자명하게 HEAD 의 조상이라 `git branch --merged` 에 뜬다: 깨끗함 시험이 없으면 worker 산출물이 스테이징도 안 된 채 가득한 worktree 가 "머지됨, 잃을 것 없음" 으로 읽히고 `--force` 로 지워진다. 잃을 것이 없는 경우는 내용이 브랜치에 있고 *그리고* 그 디렉터리에 그것 아닌 것이 없을 때뿐이다.

끝내기 전에 worktree 를 나열하고, 이번 실행이 만들었는데 아직 남아 있는 것을 보고한다. 새어 나간 worktree 는 두기는 싸고 몇 달 뒤 발견하기는 비싸다.

## 타임아웃

모든 worker 에 마감이 있다. 만료되면 아직 도는 것을 보고하고 묻는다: 더 기다림 / 끝난 것만 취함 / 중단. 이식 가능한 방식으로 계산한다: 시작 시각을 한 번 기록하고, 폴링할 때마다 경과 초를 마감과 비교한다. `timeout(1)` 도, `gtimeout` 도, 셸 종속 산술도 쓰지 않는다 — 타임아웃 로직 안의 이식성 실패는 느린 worker 를 매달린 실행으로 바꾸고, 그게 바로 이 규칙이 막으려는 유일한 실패다.
