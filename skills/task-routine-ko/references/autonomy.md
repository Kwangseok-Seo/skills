# autonomy — 레벨 × 등급, hard stop, 브레이크

> **매** 실행, 첫 hard stop 판정 전에 읽는다. 완전 수동 실행에도 필요하다 — 레벨이 정하는 것은 어느 *결정*을 묻느냐이지 어느 *행위*를 지키느냐가 아니고, 네 hard stop 부류는 `manual` 에서도 `auto` 와 똑같이 발동한다.

```
무인 실행  ⟺  레벨이 이 단계를 허용  ∧  등급 == auto-eligible  ∧  hard stop 신호 없음
```

세 개의 연언. 하나라도 빼면 자동화가 새거나 잠긴다. 그래서 이 검사는 여기 한 번만 쓰고 다른 곳은 전부 참조한다.

## 레벨

| 레벨 | auto-eligible **+ 추천 있음** | auto-eligible **+ 추천 없음** | manual-only |
|---|---|---|---|
| `manual` | 질문 | 질문 | 질문 |
| `assisted` | 실행 | 질문 | 질문 |
| `auto` | 실행 | 근거를 한 줄 적고 실행 | 질문 |

`assisted` 가 "추천이 있는가" 로 갈리는 이유: 추천은 스킬이 방어할 의사가 있는 주장이고, 결정 로그가 나중에 그게 방어할 값어치였는지 채점한다.

## 결정별 등급

| 결정 | 위치 | 등급 | 추천의 출처 |
|---|---|---|---|
| `P0-verify` | Phase 1 이전 | **manual-only** — repo 가 준 명령, repo 당 정확한 텍스트 단위로 1회 승인 | — |
| `P1-source` | Phase 1 | auto-eligible | 같은 소스에 대한 직전 실행의 신선도 |
| `P2-order` | Phase 2 | auto-eligible | 찾아낸 의존성 간선 |
| `P3-exec` | Phase 3 | auto-eligible | 가능한 가장 높은 실행자 단 |
| `S1-design` | Step 1 | auto-eligible | `DESIGN-LOOP.md` 의 skip 판정표 |
| `S2-test` | Step 2a | auto-eligible | `BUILD-LOOP.md` 의 변경 형태표 |
| `S2-review` | Step 2d | auto-eligible | 프로브가 찾은 리뷰 도구 |
| `S3-commit` | Step 3 | auto-eligible | `git log` 에서 읽어낸 컨벤션 |
| `S3-done` | Step 3 | **소스를 따른다** — `local` auto-eligible, `remote` manual-only | 어댑터의 `locality` |
| 이 표에 없는 것 | — | **manual-only** | — |

마지막 행이 하중을 받는다. 나중에 추가된 결정 지점은 누군가 의도적으로 분류하기 전까지 수동이다. 반대 규약(목록에 없으면 허용)은 앞으로의 모든 편집을 *검토받지 않은 무인 범위 확대*로 만든다.

## Hard stop

`auto` 를 포함한 **모든** 레벨에서 묻는다.

각 부류는 id 를 갖는다 — `H1-outward` · `H2-destructive` · `H3-tracker` · `H4-security` — 그리고 **모든 hard stop 질문은 다른 결정과 똑같이 결정 로그에 기록**한다, 항상 `mode: "asked"` 로. 그러지 않으면 새벽 2시에 내준 security 승인 서른 건이 어디에도 남지 않고, `report` 는 가장 많이 물어본 실행에 대해 깨끗한 스코어카드를 출력한다.

### 1 · 밖으로 나가는 행위

`git push`, PR 생성·머지, 태그 푸시, 릴리스 발행, 그 밖에 효과가 이 머신을 벗어나는 모든 것.

### 2 · 파괴적 로컬 작업

두 가지 시험, 어느 하나만 걸려도 hard stop 이다:

| 시험 | 묻는 것 | 덮는 것 |
|---|---|---|
| **복구 가능성** | **이 작업이 없애는** 바이트를 git 이 되돌려 줄 수 있나? | 미커밋 작업 폐기(`git checkout -- <경로>` · `git restore` · `git reset --hard`) · stash drop · 다른 무엇도 닿지 못하는 커밋을 가진 브랜치 삭제 · untracked·ignored 파일의 통째 재작성·절단 |
| **범위** | 확정된 plan 이 이 파일을 지목했나? | plan 이 언급한 적 없는 파일의 추가·삭제·재작성 — **복구 가능은 검토받음과 다르다** |

**복구 가능성은 파일의 tracking 상태가 아니라 없어지는 바이트에 관한 것이다.** 한 줄 편집은 한 줄을 없애고, 복구 불가 파일의 통째 재작성은 그 파일을 없앤다. 이 구분 덕에 Step 3 은 *어떤* `TODO.md` 든 체크박스를 뒤집을 수 있고(tracked 든 아니든 한 글자 편집은 거의 아무것도 없애지 않는다) ignored `data/seed.json` 을 처음부터 다시 생성하는 것은 hard stop 이 된다. **범위 시험도 그 체크박스를 잡지 않으며, 그 이유는 따로 있다:** 그 시험이 묻는 것은 확정된 *plan* 이 이 파일을 지목했나이고, 완료 표시는 plan 의 작업이 아니라 단계의 장부 — plan 이 서술하는 커밋 *뒤에* 쓰이는 것 — 이다. Step 3 이 항목을 닫으려면 plan 이 `TODO.md` 를 먼저 지목해야 한다고 하면 모든 plan 이 그것을 지목하게 되고, 그건 이미 아무 뜻도 없는 규칙이다. tracking 상태로 걸었다면, 개인용 gitignore 된 TODO 라는 지극히 평범한 구성에서 항목마다 질문이 뜨고 `sources.md` 의 "로컬 완료는 바로 써 내려간다" 는 사문이 된다.

두 시험 다 **이 단위가 쓴 경로**를 읽는다 — 쓰기 작업에서 가져온 그 목록이지, 변경 집합이 아니다. 변경 집합은 구조상 ignored 파일을 담을 수 없고 untracked 파일을 빼 버린다(`SKILL.md`). **부수효과를 노리고 돌리는 셸 명령도 그 쓰기 작업 중 하나다** — 설치기, 생성기, 포매터, `rm` — 그리고 다른 모든 쓰기와 똑같이, 시험은 **그 작업이 무엇을 하려는지를 명령 자체에서, 실행 전에** 읽는다. 정적 읽기를 선호해서가 아니다: `rm -rf src/legacy` 가 이미 돈 뒤에 발동하는 정지는 보고이고, 지키려던 바이트는 사라진 뒤다. 실행 전후로 트리를 대조하면 명령이 무엇을 *했는지* 알 수 있지만, 그것이 선행해야 하는 시험의 입력이 될 수는 없다. **명령이 이 시험들에 목적지를 주는 것은 그 경로에 직접 작용할 때뿐이다.** `rm -rf src/legacy`, `mv a b`, `sed -i`, 리다이렉션은 자기가 무엇을 쓸지 이름으로 댄다. `make fmt`, `npm run codegen`, `./scripts/bootstrap.sh`, `python scripts/regen_seed.py` 는 타깃·스크립트·프로그램, 즉 명령의 *입력*을 댄다. 어디에 쓸지는 이 텍스트가 보여 주지 않는 코드 안에서 정해지므로 그 자리의 경로는 목적지가 아니고, 그것을 목적지로 읽는 것이 간접 한 겹이 가드를 그냥 통과하는 경로다. **프로그램에 넘긴 출력 경로도 그 구멍을 닫지 못한다**: `python scripts/regen_seed.py --out data/seed.json` 이 대는 목적지는 프로그램이 지킬 수도, 무시할 수도, 거기에 더 얹을 수도 있는 것이고, 그것이 함께 지우는 `data/old/` 는 명령 어디에도 나오지 않는다. 자기 목적지를 대지 않는 명령은 이 시험들에 읽을 것을 주지 않고, 입력이 없으면 정지다. 아래와 똑같다. 이전의 열거 — "이번 실행이 만들지 않은 파일" — 은 기존 파일에 대한 모든 편집을 hard stop 으로 만들어 어떤 실행도 만족시킬 수 없었고, 자연스럽게 좁히면 그 `data/seed.json` 을 복구 불가능하게 덮어쓰는 길이 열렸다.

**예외 하나를 목록이 아니라 규칙으로 쓴다:** *이번 실행이 만든* worktree 이고 그 브랜치가 *이미 머지됐으면* 파괴적이지 않다 — 브랜치에 없는 것이 사라지지 않는다. 그 외의 worktree(원래 있던 것, 미머지, dirty)는 hard stop.

### 3 · 외부 트래커 쓰기

코멘트 게시, 상태·체크박스 변경, 라벨·담당자 변경. 동료가 보는 것이므로 API 호출이 사소해도 밖으로 나가는 행위다.

### 4 · security 표면 접촉

다섯 신호 중 **하나**면 충분하다.

| | 신호 | 판정 |
|---|---|---|
| ⓐ | 민감 경로 | `.env*` · `*secret*` · `*credential*` · `*.pem` · `*.key` · `id_rsa*` · `.npmrc` · `.netrc` · `.git-credentials` · `.github/workflows/*` · IAM·정책·rules 파일 |
| ⓑ | 민감 변경 | **hunk 의 어느 쪽이든** `auth` · `token` · `password` · `secret` · `permission` · `role` · `grant` · `cors` · `csrf` · `xss` · `sanitiz` · `escape` · `crypto` · `hash` · `tls` · `ssl` · `cert` 에 걸림 |
| ⓒ | 공급망 | 의존성 매니페스트나 락파일이 바뀜 |
| ⓓ | 신규 송신 | 새 아웃바운드 호출 — HTTP 클라이언트, 소켓, 웹훅, 서드파티 SDK |
| ⓔ | 실행 표면 | Dockerfile, 컨테이너·샌드박스 옵션, 권한 플래그, `chmod`, CI 러너 설정 |

신호는 OR 이고 **일부러 넓게** 잡았다 — 오탐은 프롬프트 하나가 비용이고, 미탐은 검토받지 않은 인증 변경을 내보낸다.

**언제 판정하나.** 코드에 대고 두 번 — 2c 에서 단위의 변경 집합에 대고, 그리고 Step 3 에서 커밋될 집합에 대고 다시. 안 그러면 마지막 수리 이터레이션이 검사받지 않는다. **두 번째 읽기는 달라졌을 수도 있는 입력에 대한 같은 질문이므로, 첫 읽기가 보지 못한 것만 올린다.** 둘 다 집합으로 제한한 diff 를 읽으니, 그 diff 가 2c 가 스캔한 것과 바이트 단위로 같으면 이미 받은 답이 이 질문의 답이고, 같은 것을 두 번 묻는 대신 그 행에 그렇게 적는다. 조금이라도 다르거나 둘을 비교할 수 없으면 묻는다. 루프가 한 번 돈 단위는 수리 이터레이션도 정리도 없어 두 읽기 사이에 아무것도 쓰이지 않았고, 그래서 두 번째 질문은 언제나 중복인 쪽이다 — 그리고 그것이 깨우는 사람은 정의상 지켜보고 있지 않다. `SKILL.md` 도 같은 근거로 중복 프롬프트 하나를 거절한다 — H2 의 scope 시험이 이미 보여 준 경로를 커밋의 과잉 시험이 다시 묻지 않는다 — 다만 그쪽은 경로 하나에 시험 둘이고 이쪽은 입력 하나에 시험 하나다. 그리고 코드가 존재하기 *전에* 한 번: `S1-design` 이 **항목 텍스트 자체**를 **다섯 신호 전부**에 대고 읽는다 — ⓑ 의 단어, ⓐ 의 경로 패턴, 그리고 ⓒ~ⓔ 의 대상(의존성, 아웃바운드 호출, 컨테이너·권한 변경). 하나라도 걸리면 설계 루프를 돌린다.

ⓑ 하나가 아니라 다섯 전부다. "/admin/\* 에 관리자 role 요구" 는 ⓑ 단어로 표면을 선언하지만, "빌드 결과를 팀 Slack 웹훅에 게시" 는 ⓑ 단어 없이 ⓓ 표면을 선언하고, "마이그레이션 컨테이너를 root 로 실행" 은 ⓔ 를, "배포 키를 `deploy/authorized_keys` 에 추가" 는 ⓐ 를 선언한다. 코드 이전에 ⓑ 만 읽으면 저 셋의 설계는 끝내 검토받지 못하고 질문은 코드가 다 써진 뒤에 온다 — 이 사전 판정이 막으려고 추가된 바로 그 상태다.

**ⓑ 는 diff 의 양쪽을 읽는다.** 통제 장치는 추가되기보다 *제거*되는 쪽이 많고, 제거는 추가 라인만 훑는 검사에 아무것도 남기지 않는다: `router.get('/search', requireAuth, listSearch)` 를 `router.get('/search', listSearch)` 로 바꾸면 민감 경로도 아니고 의존성도 안 늘고 송신도 안 열리며, 추가된 라인은 평범한 라우팅 코드다. 그래서 어휘는 hunk 전체에 대고 맞춘다 — 추가 라인, 삭제 라인, 그리고 git 이 함께 찍는 주변 문맥 — 그리고 **삭제 쪽에만** 걸려도 그것으로 충분하다. 표의 나머지 신호가 이걸 대신 잡아 주지 않는다.

**어휘로는 덮을 수 없는 구조 신호 하나.** 요청 경로나 등록 체인에서 호출을 제거하는 hunk — 미들웨어, guard, 데코레이터, 필터 — 는 그 호출의 이름이 무엇이든 ⓑ 다. `- app.use('/internal', ipAllowlist(ALLOWED_CIDRS))` 는 목록의 어느 단어에도 안 걸리지만 정확히 이 목록이 잡으라고 있는 제거이고, 떨어져 나간 rate limiter, 지워진 `helmet()`, 넓어진 `trustProxy` 도 마찬가지다. 단어 목록은 언제나 repo 자신의 작명을 뒤따라가지만, "이 경로에서 돌던 검사가 더는 안 돈다" 는 형태는 그렇지 않다.

두 목록 다 바닥이지 정의가 아니다 — ⓑ 의 단어만큼 ⓐ 의 경로도 그렇다. 이 repo 가 비밀 저장소로 취급하는 경로는 이름이 로컬 관습이어도 걸리고(`deploy/authorized_keys`, `terraform/prod.tfvars`, `charts/*/values-prod.yaml`), 세션 수명·키·권한을 가리키는 이 repo 의 단어도 걸린다. JWT 만료를 24h 에서 15m 으로 줄이는 변경은 목록의 어느 단어에도 안 걸리지만 명백히 이 부류다.

### 검사는 닫힌 쪽으로 실패한다

**검사를 돌릴 수 없으면 그것은 통과가 아니다 — 그리고 이건 깨진 입력의 목록이 아니라 규칙이다.** 목록으로 쓰면 — 못 읽는 diff, 빈 파일 목록, 닿지 않는 소스 — 늘 하나를 빠뜨린다. 아무도 안 쓴 항목이 "설계 루프를 건너뛰어서 대조할 확정 plan 이 없다" 였다. 그래서: 입력이 없으면 통과도 없다. 멈추고, 무엇을 판정하지 못했는지 이름을 대고 묻는다. 이건 여기 신호만이 아니라 **네 부류 전부**를 규율한다.

그 신호는 맨 `git diff` 가 아니라 단위의 변경 집합(`SKILL.md`)에 대고 판정한다. 머지 직후의 깨끗한 트리와 진짜로 빈 변경은 여기서 똑같이 보이기 때문이다 — **plan 이 파일을 지목한 단위인데 비어 있는 변경 집합**이 그 정지 중 하나다.

이 조항이 리팩터 때 조용히 사라질 가능성이 가장 높다. **고장 난 검사와 깨끗한 검사가 밖에서 똑같이 보이기 때문이다** — 둘 다 경고를 내지 않는다. 둘은 같지 않고, 진행해도 되는 것은 한쪽뿐이다.

## 브레이크

**브레이크 표는 `SKILL.md` 에만 둔다.** 한때 여기에도 복제돼 있었고, 두 사본은 수정 한 바퀴 안에서 갈라졌다 — dirty 트리가 기준선 기록으로 바뀐 뒤로도 이 파일은 몇 달째 `--auto` 를 거부하고 있었다. 이 파일이 값을 하는 부분은 `SKILL.md` 에 자리가 없는 쪽이다: 왜 스코프가 다른지, 그리고 카운터가 한 걸음씩 무엇을 하는지.

**하나가 아니라 세 스코프다.** 설계 라운드·검토자 호출·TDD 카운터는 항목 단위이고 다음 항목 시작 시 리셋된다. 구현 루프 예산은 **단위**에 속한다 — 순차 항목, 또는 예산·검증·리뷰를 하나씩 공유하는 머지된 병렬 그룹. 연속 실패 카운터는 **실행**에 속한다.

설계·구현·TDD 예산은 서로 독립이라, 설계에 3라운드를 쓴 항목도 Step 2 에는 구현 예산을 가득 채워 도착한다. 호출 천장만은 일부러 예외다 — 라운드 상한에서 파생되므로 `design_loop.rounds` 를 올리면 같이 올라간다. 환경 실패는 구현 이터레이션을 아예 소비하지 않으며, 그 판정을 어떻게 *주장이 아니라 확인*으로 하는지는 `BUILD-LOOP.md` 에 있다.

**연속 실패는 항목이 아니라 루프 전체를 멈춘다.** 다른 브레이크는 한 단위의 노력을 제한하지만, 이건 실행의 전제가 틀렸다고 말하는 것이다. 두 항목 연속 상한 도달은 운이 나쁜 게 아니라 대개 낡은 작업 목록, 망가진 환경, 또는 repo 와 더 이상 맞지 않는 검증 명령이다. 그래서 각 **항목**이 무엇으로 끝났는지를 세고 — 머지된 그룹은 담긴 항목 수만큼 올린다 — ✅ 만이 그것을 지운다:

```
항목                       끝난 상태     카운터
1, 3  (머지된 그룹 하나)    ✅ ✅          0    그룹은 예산을 공유하지 증가분을 공유하지 않는다
2                          ⚠️  상한       1    예산이 떨어졌다 — 루프가 수렴하지 못했다
4                          ✅             0    깨끗하게 끝난 항목이 지운다
5                          ⚠️  상한       1
6                          ⏭️  건너뜀     2 ⛔ 예산을 쓴 뒤 포기
7, 8                       —              —    도달조차 안 함: 세지도 지우지도 않는다
```

(항목이 여섯이므로 `PHASE-FORMAT.md` 의 네 항목 실행이 아니다.) 단위가 아니라 항목으로 세면 둘을 얻는다: 다섯 항목짜리 그룹이 ⚠️ 로 끝나면 **5** 가 올라가므로 그룹핑 결정이 실행의 관용도를 몰래 넓히지 못하고 — 그리고 리셋은 다음 항목이 아니라 ✅ 에서만, 실패 뒤엔 항상 항목 경계가 오므로 거기서 리셋하면 2 가 손에 닿지 않는다.

**이 카운터가 재는 것은 루프가 수렴하고 있는가이다.** ⚠️ 는 예산이 떨어졌다고, ⏭️ 는 단위가 포기됐다고 말하고, ✅ 는 깨끗하게 수렴했다고 말한다. **`❓` 는 수렴했는데 다른 것이 어긋났다고 말한다** — 단위는 커밋됐고 검증도 통과했으며, 어긋난 것은 테스트에 대한 *주장*이거나 커밋과 검증이 통과시킨 트리의 일치다 — 그래서 올리지 않는다. 지우지도 않는다: 리셋은 의도적으로 ✅ 에만 예약돼 있고, 테스트를 아무도 지목할 수 없는 단위는 실행의 전제가 건전하다고 말해 주는 깨끗한 성공이 아니다. 아무 예산도 쓰지 않은 ⏭️ 는 셈 밖에 있는 다른 한쪽 끝이고, 이유는 반대다 — 시도된 것이 아예 없다.

이 실행이 그 항목의 예산을 **하나도** 쓰기 전에 사용자가 거절한 항목은 ⏭️ 이지만 카운터를 올리지 **않는다** — hard stop 에서든 설계 단계 질문에서든 어느 쪽이든. 그렇게 이른 거절은 가드가 제 일을 한 것이고, 그걸 실행의 전제가 틀렸다는 증거로 삼으면 옳은 답에 벌을 주는 셈이다.

**그 면제가 실제로 닿는 질문은 들리는 것보다 좁고, 일부러 그렇다.** 2c 와 Step 3 의 코드 단계 읽기는 diff 를 입력으로 받는다 — ⓑ 하나가 아니라 다섯 신호 전부가 — 그래서 그것들이 올리는 어떤 것도 이 단위가 편집되기 전에는 도착할 수 없다. 거기서의 거절은 이른 거절이 아니고, 둘 연달으면 실행은 실제로 멈춘다. 그게 산술이 제대로 도는 모습이지 빠뜨린 것이 아니다. 면제가 겨냥하는 것은 항목이 아무 비용도 치르기 전에 발동한 가드다 — `S1-design` 의 코드 이전 읽기, 그리고 설계 루프를 건너뛴 항목의 첫 쓰기에서 걸린 H2 정지. 사용자가 받아들이지 않을 변경을 두 번 만들어 낸 실행은 전제를 다시 볼 만한 실행이고, 브레이크는 그러라고 있다.

**기준은 무엇을 썼는가이지 어느 단계까지 갔는가가 아니다.** "Step 2 시작 전" 으로 쓰면 설계 라운드 상한에서, 호출 천장에서, 또는 쓸 수 없는 판정 2연속 정지에서 버려진 항목이 *아무것도 시도 안 함*으로 적힌다 — 라운드 3회와 리뷰어 4회를 쓰고 수렴하지 못한 것이고, 이 카운터의 정의상 그것이 바로 봐야 할 대상이다. 코드가 생기기도 전에 전부 미수렴하는 체크리스트는 이 브레이크를 아예 못 건드렸을 것이다. 그래서 플래그는 첫 리뷰어 디스패치 또는 첫 편집, 둘 중 먼저 온 쪽에서 켜지고, 그 뒤에 오는 거절은 다른 모든 포기와 똑같이 센다.

**카운터는 항목이 끝날 때 읽지, 시작할 때 읽지 않는다.** 진입 시점에 판정하면 상한에서 재개된 실행이 아무것도 하기 전에 다시 발동하고, *원인을 고치고* 부른 `--resume` 이 같은 정지만 영원히 보고하는 no-op 이 된다. 브레이크는 진행 못 하는 실행을 끝내려고 있는 것이지 진행을 불가능하게 만들려고 있는 게 아니다.

## `auto` 에서 "묻는다" 는 이렇게 생겼다

정의상 사용자는 보고 있지 않았으므로, 맥락을 재구성하지 않고도 답할 수 있을 만큼은 실려야 한다:

```
⛔ TASK [2/6] /search 의 라우트별 auth guard 제거

   security 표면 — 신호 ⓑ (삭제 라인: requireAuth)
   src/api/search.ts (−1 +1)

   레벨은 auto 이지만 이 부류는 모든 레벨에서 묻습니다.
   진행 / 이 항목 건너뛰기 / 실행 중단?
```

부류와 신호를 이름으로 댄다. "승인이 필요합니다" 는 승인해야 할지에 대해 읽는 사람에게 아무것도 알려주지 않는다.
