# setup — 첫 실행, config, 능력 프로브

> 첫 실행(어디에도 config 가 없음) 또는 `task-routine setup` 호출 시 읽는다. config 가 생긴 뒤로는 다시 읽지 않는다.

## 위저드

질문 넷, 그리고 쓴다. **감지할 수 있는 것은 묻지 않는다** — 감지값을 기본값으로 보이고 그냥 넘기게 한다.

그다음은 위저드가 **왜** 돌았는지에 달렸다: `setup` 으로 명시 호출됐다면 config 를 쓰는 것으로 그 호출은 끝이다. config 가 없어서 자동으로 발동했다면, 방금 받은 답을 들고 프로브와 Phase 1 로 **이어서 간다** — 사용자가 요청한 것은 작업 실행이고, 질문 넷에 답한 것이 두 번 요청해야 할 이유가 되지는 않는다.

| # | 질문 | 제시할 기본값 |
|---|---|---|
| 1 | 작업은 어디서 오나? | repo 에 `TODO.md` 가 있으면 그것, 없으면 질문 |
| 2 | 변경은 어떻게 검증하나? | repo 지문 (`BUILD-LOOP.md` §2c) — 그냥 넘기는 행위가 그 명령에 필요한 **승인 그 자체**다. 지문이 아무것도 못 맞히면 넘길 기본값 자체가 없다: 그냥 묻고, 직접 친 답이 3단이며 친 행위가 곧 승인이다 |
| 3 | 얼마나 무인으로 돌릴까? | `assisted` |
| 4 | 무인 실행 1회가 처리할 항목 수는? | `5` |

3번은 묻기만 할 게 아니라 설명해야 한다 — 비용이 앞에서 안 보이기 때문이다:

```
manual     모든 결정은 당신 것
assisted   추천이 붙은 선택은 알아서 진행, 나머지는 당신에게
auto       auto-eligible 전부 알아서 진행 — 기본값이 아니고, 절대 눌러앉지 않는다:
           --auto 는 1회 실행에만 적용되고 여기에 기록되지 않는다
```

## Config

파일 둘. 프로젝트가 전역을 이기되 **키 단위**다 — `verify.command` 하나만 적은 프로젝트도 전역의 자율성 레벨을 그대로 물려받는다. 좋든 싫든 물려받는다: 어떤 키가 아래 표의 어느 쪽에서 올 수 있는지는 `SKILL.md` 의 신뢰 분리가 정하고, 어떤 repo 도 그걸 다시 협상할 수 없다.

```
~/.claude/task-routine/config.json     전역 — 위저드가 쓴다
<repo>/.claude/task-routine.json       프로젝트 — 선택, 커밋해서 팀과 공유
```

```json
{
  "version": 1,
  "source": { "adapter": "markdown", "path": "TODO.md" },
  "verify": { "command": "npm test" },
  "autonomy": { "level": "assisted" },
  "auto": { "max_tasks": 5, "consecutive_failures": 2 },
  "design_loop": { "rounds": 3, "reviewer": "auto" },
  "build_loop": { "iterations": 3, "tdd_attempts": 15 },
  "execution": { "timeout_minutes": 20,
                 "executor": { "command": "herdr", "session_env": "HERDR_ENV" } },
  "capabilities": { "probed_at": "2026-08-16T09:14:00+09:00",
                    "present": ["git", "gh", "node"], "absent": ["herdr", "tdd"] }
}
```

모든 키는 선택이고, 빠지면 위 기본값이 적용된다. 이 빌드가 모르는 `version` 은 보고하되, 아는 키만 최선으로 읽는다 — 통째로 거부하지 않는다. 오래된 스킬이 새 config 를 만나는 것은 세상의 정상 상태다. `reviewer: "auto"` 는 "가능한 가장 높은 단" 을 뜻한다 — 특정 도구로 못박는 것은 이유가 있을 때만.

`execution.executor` 는 실행자 사다리의 1단에 닿게 하는 유일한 것이고, 기본값이 없다: **아무도 쓰지 않았으면 1단은 존재하지 않는다.** 두 필드가 다 필요하다 — `command` 는 프로브가 `PATH` 에서 찾을 이름이고, `session_env` 는 그것이 설정돼 있고 비어 있지 않다는 사실이 곧 살아 있는 세션을 뜻하는 변수의 이름이다 — 그리고 `session_env` 없는 `command` 는 살아 있음을 판정할 입력이 없으므로 2단에 머물고 그 이유를 말한다. 형식이 아니다: 1단의 근거 전체가 *사용자가 세팅해 두고 보고 있다* 이고, 살아 있는 세션의 신호를 내놓지 않는 도구는 그 뒷절반을 증거할 수 없다. 전역 파일 키인 이유는, repo 가 이 실행이 worker 를 띄우는 바이너리의 이름을 대서는 안 되기 때문이다 — 자기 테스트 명령을 대는 것과는 다른 질문이고, 그쪽은 `BUILD-LOOP.md` §2c 가 요구하는 승인 아래 `verify.command` 가 답한다.

| 키 | 올 수 있는 곳 |
|---|---|
| `version` · `source` · `verify.command` | 전역 **또는** 프로젝트 — 프로젝트에 관한 사실 |
| `autonomy.level` | 전역, 또는 1회 실행에 한해 `--level` / `--auto` |
| `auto.*` · `design_loop.*` · `build_loop.*` · `execution.*` | **전역 파일만** — 이들엔 플래그가 없고, 프로젝트가 자기 상한을 올릴 수 없다 |
| `capabilities` | 프로브가, 전역 파일에만 — 이 머신을 기술하는 값이지 프로젝트 사실이 아니다 |

위저드는 전역 파일을 쓰므로 양쪽 다 쓸 수 있다. 오른쪽 키를 담은 프로젝트 파일은 병합하지 않고 보고한 뒤 무시한다. 아예 파싱되지 않는 프로젝트 파일은 보고하고 **전체를** 무시한다 — 프로젝트 config 를 버리는 것은 무인 실행 범위를 좁힐 뿐 넓히지 않으므로, 그렇게 실패하는 것은 추측하는 것과 달리 안전하다.

## 비밀은 config 에 담지 않는다

값이 아니라 **환경변수 이름**을 적는다:

```json
{ "source": { "adapter": "github", "repo": "owner/name", "token_env": "GITHUB_TOKEN" } }
```

프로젝트 config 는 커밋해 공유하라고 있는 파일이다. 그건 비밀이 하나도 없을 때만 안전하다 — 그래서 자격증명처럼 생긴 것(`token`·`key`·`secret`·`password` 류 키 아래의 길고 불투명한 문자열)이 config 에서 발견되면 **말하고 멈춘다.** 그냥 진행하면 매 실행 그것을 읽게 되고 언젠가 보고서에 찍힌다.

## 능력 프로브

셋업 때만이 아니라 **매 실행** 돈다.

| 층 | 방법 | 비고 |
|---|---|---|
| 외부 CLI | `command -v <이름>` · PowerShell `Get-Command <이름> -ErrorAction SilentlyContinue` | `git`, `gh`, 설정돼 있으면 `execution.executor.command` |
| 스킬·에이전트 | `~/.claude/skills/*/`, `~/.claude/agents/*.md`, 프로젝트 `.claude/` 열거 | `tdd`·리뷰·simplify 도구를 여기서 찾는다 |
| 플러그인 | `~/.claude/plugins/installed_plugins.json` — `{"plugins": {"<이름>@<마켓>": [{"installPath": …}]}}` | v2 스키마 |
| 네이티브 | 없음 — `git worktree` 는 항상 있다 | 서브에이전트가 실행자 계약을 만족하는지는 `execution.md` 가 답할 질문 |

프로브가 대조하는 스냅샷은 위의 `capabilities` 키다 — 매 실행 후 프로브가 쓰고, 손으로 고치지 않고, 진실로 읽지 않는다. **변화를 감지하기 위한 캐시이지 진실의 원천이 아니다.** 능력 목록을 config 에 복제하고 그걸 믿는 것이 바로 저장된 목록과 실물이 갈라지는 경로다 — 사용자가 도구를 깔았는데 스킬이 모르거나, 지웠는데 계속 그리로 보낸다.

```
능력    git 2.45 ✓ · gh ✓ · node ✓ · herdr ✗ · tdd 스킬 ✗
변화    지난 실행엔 herdr 가 있었고 지금은 없다 → 병렬이 2단으로 내려감
```

두 번째 줄이 재프로브의 존재 이유다. 바뀐 게 있으면 출력하고, 없으면 아무것도 출력하지 않는다. 맨 처음 프로브에는 비교할 스냅샷이 없는데, 그건 변화가 아니다 — 스냅샷을 쓰고 첫 줄만 출력한다.

### 프로브가 하면 안 되는 것

- **아무것도 설치하지 않는다.** 프로브는 세계를 보고하지 조정하지 않는다.
- **동작 확인을 위해 도구를 돌리지 않는다.** `--version` 이나 `--help` 가 검사의 전부다. 그 이상은 부수효과가 있다.
- **프로브 실패는 "없음" 을 반환하는 것이지 실행을 멈추는 게 아니다.** 프로브는 게이트가 아니다 — 게이트는 따로 있고, 부재는 이미 "강등하고 말한다" 로 처리된다.
