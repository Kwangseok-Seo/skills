# BUILD-LOOP — Step 2 의 구현 / 검증 / 리뷰 루프

> Step 2 진입 시, 또는 아래 지문 표가 필요한 셋업 위저드 2번 질문에서 1회 읽는다. **게이트** — 검증 통과 뒤에만 리뷰, 정리는 출구에, 무엇을 안 깎는가 — 는 `SKILL.md` 에 있다. 이 파일은 도구 감지, 범위, 출력 형태다.

```
2a 전략 → 2b 구현 → 2c 검증 → 2d 리뷰 → (실패·지적이면 2b 로, 예산 3) → 2e 정리·확정
```

예산 하나, 루프 하나. 이 파일을 관통하는 예시는 `PHASE-FORMAT.md` 실행의 항목 2 — *목록 응답 캐싱*.

## 2a · 전략 — 한 번만 정한다

진입 시 정하고 다시 묻지 않는다. 루프는 2b 로 재진입한다. 머지된 그룹에서 그 진입 시점은 **worker 를 띄우기 전, 항목마다 한 번**이다 — 머지 뒤라면 전략을 worker 산출물이 이미 보이는 상태에서 고르게 된다(`references/execution.md`). 선택지보다 **판단 근거를 먼저** 제시한다 — 근거가 안 보이는 추천은 반대할 수도 없다.

| 변경 형태 | unit | integration | TDD |
|---|---|---|---|
| 순수 함수, 경계 없음 | 필요 | 불필요 | 옵션 |
| 비즈니스 규칙·검증·상태 전이 | 필요 | 경우에 따라 | **추천** |
| 저장소나 타 서비스를 건드리는 엔드포인트 | 경우에 따라 | 필요 | 옵션 |
| 데이터 상태 변경(남이 읽는 값을 쓴다) | 필요 | 필요 | **추천** |
| 스케줄러·배치·워커 | 필요 | 경우에 따라 | **추천** |
| 필드 추가·매핑·이름 변경 | 불필요 | 불필요 | **노출 안 함** |
| 문서·주석·포맷 — 동작이 실리지 않음 | 불필요 | 불필요 | **노출 안 함** |

필드 이름 바꾸는 데 TDD 는 엄밀함의 옷을 입은 간접비다. 이름 변경 행이 아예 노출하지 않는 이유이고, 그 아래 문서 행도 마찬가지다.

**TDD 인계.** TDD 를 골랐고 프로브가 `tdd` 스킬이나 rule 을 찾았으면 그것을 따르고 방법론을 여기서 재진술하지 않는다. 아무것도 못 찾았으면 재량으로 하되, 방법론이 가져갈 수 없는 불변식 셋은 지킨다:

- behavior 는 *public interface 를 통해 관찰*하지 내부 상태를 들여다보지 않는다
- 다음 behavior 는 직전 것이 통과한 뒤에만 시작한다
- **시도 예산은 behavior 가 아니라 항목에 속한다.** `min(build_loop.tdd_attempts, 2a 에서 지목한 behavior 수 × 5)` — 기본값 15 — 이고, 전략을 고를 때 고정된다. 이걸 상한으로 만드는 것은 그 평평한 항이다: 곱해지는 수를 상한 대상이 직접 고르는 곱은 상한이 아니다 — 검증 항목에 behavior 를 열둘 적으면 "behavior 당 5" 는 조용히 무인 시도 60회가 된다. behavior 당 상한만으로는 상한이 아니다 — behavior 개수를 정하는 것이 방법론이므로 16개면 80회를 사게 되고, 그중 무엇도 구현 루프 이터레이션이 아니다. 나중에 behavior 를 쪼개면 그 예산이 나뉠 뿐 늘지 않는다. 위임한 방법론은 *어떻게* 반복할지를 정하지 *얼마나 오래* 를 정하지 않는다

**시도 1회는 구현이 놓인 상태로 그 behavior 의 검사를 돌리는 것으로 끝나는 한 사이클이다.** 새 behavior 의 첫 red 실행 — 방법론이 존재하는 이유인 바로 그 단계 — 은 시도가 아니다. 그것을 세면 behavior 를 *충족*하는 데가 아니라 *진술*하는 데 예산을 쓰게 되고, `tdd_attempts` 가 낮으면 상한이 구현이 하나도 존재하기 전에, 그 단계가 만들어 내라고 요구한 바로 그 red 스위트 위에서 발동한다. 예산 1로 걸어 봤다: red 실행과 그것을 green 으로 만든 구현이 한 읽기에서는 시도 1회였고 다른 읽기에서는 2회였는데, 여기 그 둘을 가르는 문장이 없었다. 그렇다고 red 실행이 무제한이 되는 것은 아니다 — behavior 수가 그것을 묶고, 그 수는 이미 예산의 나머지 절반이다. 검사를 다시 돌리는 refactor 는 다른 것과 똑같이 시도 1회다: 예산이 묶는 것은 실패만이 아니라 그 항목에 들이는 작업이다.

**상한은 두 가지로 발동하고, 어느 쪽이었는지가 어떤 선택지에 의미가 있는지를 정한다.** green 이 되지 않는 behavior 가 예상된 쪽이다. 다른 쪽은 *다음* behavior 를 시작할 여유가 없는 예산이다: behavior 둘과 예산 1로 걸어 보니 behavior 1이 green 이 된 자리에서 아무것도 실패하지 않았고 재시도할 것도 없는 채로 항목이 멈췄다. *시도 1회 추가*는 첫째에, *TDD 를 해제하고 항목을 통상 방식으로 끝내기*는 둘 다에 답하고, *재설계*는 예산이 덮지 못하는 것이 behavior 목록 자체일 때 어느 쪽에도 답하지 못한다 — behavior 를 쪼개면 예산이 나뉠 뿐 늘지 않는다.

테스트 명령을 돌릴 수 없는 실행자에서는 TDD 가 불가능하다. 2c 에서 발견하지 말고 2a 에서 말한다.

**이 선택은 단위가 실제로 낸 것에 대고 검사된다.** `none` 이 아닌 것은 전부 이 단위가 테스트를 낼 거라는 주장이고, Step 3 이 이 단위가 쓴 경로를 읽어 그런지 본다(`SKILL.md`). 그래서 `none` 은 **테스트가 아예 필요 없는 두 행**에 대한 옳은 답이다 — 그리고 그 답은 나중에 테스트가 없는 것으로 드러날 때가 아니라, 여기서 변경 형태를 보고 내린다.

## 2b · 구현

minimal-first, 이 순서로: 이미 있는 것 재사용 → 표준 라이브러리 → 플랫폼 → 의존성 → 한 줄 → 되는 최소.

재진입 시에는 직전 이터레이션의 실패·지적이 요구한 것**만** 구현한다. 이터레이션은 설계를 다시 열라는 초대가 아니다 — 그건 Step 1 에서 확정됐고, 여기서 다시 열면 두 예산을 모두 빠져나간다.

## 2c · 검증

명령을 이 순서로 해석하고, 어느 단을 썼는지 보고한다:

| 단 | 출처 |
|---|---|
| 1 | 프로젝트 config 의 `verify.command`, 다음 전역 config |
| 2 | repo 지문 (아래) |
| 3 | 1회 질문하고 답을 config 에 써서 다시 묻지 않는다 |

**프로젝트 config 에서 온 1단과 모든 2단 명령은 repo 와 함께 온 텍스트**이고, 이 루프는 그것을 이터레이션마다 실행한다. 해석된 명령을 출처와 함께 보이고 이 repo 에서 처음 돌기 전에 예스를 받는다 — 정확한 텍스트 단위로 1회, `P0-verify` 로 기록 (`SKILL.md` §런타임 레이아웃). 전역 config 의 1단과 3단은 사용자가 직접 친 것이고, 친 행위가 승인이었다.

| 지문 | 기본 명령 |
|---|---|
| `package.json` | `test` 스크립트, 없으면 `npm test` |
| `build.gradle` / `build.gradle.kts` | `./gradlew test` · Windows 는 `.\gradlew.bat test` |
| `pom.xml` | `mvn -q test` |
| `Cargo.toml` | `cargo test` |
| `pyproject.toml` / `setup.cfg` / `pytest.ini` / `tox.ini` | `pytest` |
| `go.mod` | `go test ./...` |
| `test` 타깃이 있는 `Makefile` | `make test` |

**최초 검증은 공짜다.** 카운터는 *수리*를 제한하려고 있지, 사실을 알아내는 값을 물리려고 있는 게 아니다.

**환경 실패는 이터레이션이 아니고, 그 분류는 주장이 아니라 확인 대상이다.** 환경 실패로 치는 조건은 **같은 명령이 단위의 시작 커밋에서도 똑같이 실패할 때**뿐이다 — 거기서 돌려 보고 대조한다. 지금 트리를 옮기지 말고 일회용 worktree 에서 돌린다: `git worktree add --detach <경로> <단위 시작 커밋>` 로 만들어 돌리고 지운다. **인자 둘, 이 순서로.** 커밋만 주면 git 은 그것을 *경로*로 읽어 해시 이름의 디렉터리를 만들고 그 안에 HEAD 를 체크아웃한 뒤 exit 0 하므로, 대조가 HEAD 대 HEAD 가 되어 모든 실패가 환경으로 분류된다. **그 경로는 repo 밖에 둔다.** 안에 두면 이 단위가 기준선을 뜬 *뒤에* 생긴 untracked 디렉터리라 **이 단위 자신의** 변경 집합에 들어가고, 그 커밋에서 과잉 프롬프트를 부른다.

그 제거는 묻는다 — `references/autonomy.md` §2 의 예외가 닿지 않는 모든 worktree 제거와 같다. 닿지 않는 이유는 detached worktree 에 브랜치가 없어 그 규칙의 "브랜치가 머지됨" 시험이 평가할 것이 없기 때문이다. 환경 판정이 연속 2회면 이미 멈추고 묻게 되어 있으므로 프롬프트 비용은 묶여 있다.

**그 worktree 에서 명령이 아예 시작조차 못 하면** — 러너도 빌드도 실행할 것이 없으면 — 분류에 입력이 없는 것이므로 말하고 묻는다. **기준선 실행이 테스트에 닿기 전에 실패하는 것도 같은 경우이고, 일치가 아니다.** 일회용 worktree 는 새 체크아웃이라 gitignore 된 것은 그 안에 아무것도 없다 — 실측: 워킹 트리에 있는 gitignore 된 디렉터리가 그 worktree 에는 없다 — 즉 설치된 의존성도, 빌드 산출물도, 생성된 파일도 없다. 거기서 나는 해석·빌드 실패는 이 단위가 돌던 환경의 성질이 아니라 그 체크아웃의 성질이다. 느슨하게 읽으면 — *둘 다 실패했으니 일치* — 그런 repo 의 모든 실패가 환경이 되고, 엄격하게 읽으면 거기서는 아무것도 확정되지 않는다. 어느 쪽이든 대조는 답을 내놓지 못한 것이고, 그렇게 말하면 된다. 판정은 기준선이 repo 자신의 검사에 닿기라도 했는가다: 아무것도 수집하지 못한 러너, 소스를 하나도 컴파일하지 못한 빌드, 의존성 해석에서 멈춘 명령. 비용은 설치된 상태가 필요한 테스트 명령을 쓰는 repo 가 무료 판정 대신 질문에 도달한다는 것이고, 그게 짐작하지 않는 값이다 — 그리고 이 대조는 *환경*이라는 판정을 주장할 때만 도는 것이라 평범하게 실패한 테스트는 그 비용을 내지 않는다. 자리를 만들려고 checkout 하거나 stash 하면, 시험 대상인 구현을 `autonomy.md` §2 가 파괴적이라 부르는 그 작업들에 통과시키는 셈이다. 아니면 Redis 를 *추가하는* 항목이 내는 `ECONNREFUSED` 가 문자 그대로 "DB 미구동" 이 되어 무제한 무료 이터레이션을 사고, 명시된 탈출구("환경이 올라오면 다시 돌린다")는 영원히 오지 않는다 — 그 조건을 만든 것이 시험 대상인 변경이기 때문이다.

환경 판정이 연속 2회면, 둘 다 확인을 통과했더라도 멈추고 묻는다. 한 바퀴 뒤에도 안 올라온 환경은 이 루프가 고칠 것이 아니고, 예산을 안 쓰고 있다는 사실이 요점이 아니다 — 실행이 요점이다.

## 2d · 리뷰

**2c 가 통과한 뒤에만** 돈다. 도구는 프로브에서 고른다:

| 있는 것 | 쓸 것 |
|---|---|
| 리뷰 스킬·플러그인 | 실행 — **이 실행의 repo 에서, 이 단위의 집합을 주고** |
| 사용자가 직접 입력해야 하는 리뷰 명령 | 명령을 정확히 출력하고 대기 — 절대 대신 호출하지 않는다 |
| 아무것도 없음 | 단위의 변경 집합(`SKILL.md`)을 plan 과 대조해 직접 리뷰 |

**표적을 이 실행의 repo 가 아닌 다른 데서 결정하는 도구는 애초에 첫 행이 아니다.** 실측: 세션에 설치된 리뷰 플러그인이 실행이 몰고 있는 repo 가 아니라 세션 자신의 작업 디렉터리를 리뷰했다 — 다른 프로젝트의 diff 를 보고 이 단위의 리뷰라고 불렀을 것이다. 한 rung 내려가고 강하를 보고한다. 도구가 아예 없는 경우와 똑같이.

**도구에는 집합을 건넨다** — 경로로든, 집합으로 제한한 diff 로든. 그렇게 범위를 못 주는 도구도 돌리기는 하지만 그것이 읽은 것은 작업 트리다. 그 사실을 말하고, 지적은 집합에 대고 직접 읽는다. 집합 밖 경로에 대한 지적은 남의 미커밋 작업이고, 그걸로 루프를 다시 여는 것은 이 단위가 하지도 않은 변경에 이 단위의 예산을 쓰는 일이다.

세 번째 행은 폴백에 대한 변명이 아니라 진짜 리뷰다. Step 1 의 plan 이 명세이고, 의도와 구현을 대조하는 것이 바로 리뷰어가 하는 일이다. 그리고 여기가 집합 대신 트리를 읽으면 조용히 실패하는 자리다 — 그룹이 머지된 뒤 트리에는 읽을 것이 없고, 없는 것에 대한 리뷰는 아무것도 보고하지 않는다.

루프를 다시 여는 지적은 **결함과 계약 위반**이다. 스타일 취향과 "이러면 더 낫겠다" 는 이터레이션이 아니라 기록으로 간다 — 아니면 취향이 정확성용 예산을 먹는다.

```
검증   npm test — 34 passed, 0 failed        (2단, package.json)
리뷰   로컬 diff vs plan                      (리뷰 도구 없음)

  1  캐시 키에 정렬 파라미터가 빠졌다 — 정렬을 바꿔 요청해도 이전 순서가 반환된다
     → 결함, 루프 재개

  2  LRU 크기가 리터럴 500
     → 취향, 기록만
```

## 2e · 정리와 확정

정리는 **루프를 2회 이상 돈 경우에만** 나타난다. 한 번에 깨끗이 끝난 구현은 정리할 것이 없고, 그래도 단계를 띄우면 사람은 그 단계를 건너뛰는 법을 배운다.

범위는 **단위의 변경 집합**이다 — `SKILL.md` 가 한 번 정의하고 2d·2e·hard stop 검사·커밋이 전부 그 하나를 읽는다. 작업 트리가 아니다: dirty 한 트리에는 이전 단위의 파일이 섞여 있고, 머지된 그룹은 깨끗한 트리를 남긴다.

정리한 뒤 같은 예산에서 재검증 1회. 거기서 실패하면 다른 이터레이션과 똑같이 루프로 재진입한다. 예산이 이미 소진됐으면 **재검증 없이** 정리만 하거나 정리를 건너뛴다 — 정리하고 검증 없이 커밋하는 경로는 없다.

```
정리   2개 파일 정리 · 재검증 통과
확정   3/3 이터레이션 — 상한 도달, 미해결 지적 1건 (Phase 4 에 ⚠️ 로 기록)
```

지적이 남은 채 확정하는 것은 허용된다. 숨기는 것은 아니다 — Phase 4 요약에 지적 원문을 붙인 ⚠️ 행이 된다.
