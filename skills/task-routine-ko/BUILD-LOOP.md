# BUILD-LOOP — Step 2 의 구현 / 검증 / 리뷰 루프

> Step 2 진입 시, 또는 아래 지문 표가 필요한 셋업 위저드 2번 질문에서 1회 읽는다. **게이트** — 검증 통과 뒤에만 리뷰, 정리는 출구에, 무엇을 안 깎는가 — 는 `SKILL.md` 에 있다. 이 파일은 도구 감지, 범위, 출력 형태다.

```
2a 전략 → 2b 구현 → 2c 검증 → 2d 리뷰 → (실패·지적이면 2b 로, 예산 3) → 2e 정리·확정
```

예산 하나, 루프 하나. 이 파일을 관통하는 예시는 `PHASE-FORMAT.md` 실행의 항목 2 — *목록 응답 캐싱*.

---

## 2a · 전략 — 한 번만 정한다

진입 시 정하고 다시 묻지 않는다. 루프는 2b 로 재진입한다. 선택지보다 **판단 근거를 먼저** 제시한다 — 근거가 안 보이는 추천은 반대할 수도 없다.

| 변경 형태 | unit | integration | TDD |
|---|---|---|---|
| 순수 함수, 경계 없음 | 필요 | 불필요 | 옵션 |
| 비즈니스 규칙·검증·상태 전이 | 필요 | 경우에 따라 | **추천** |
| 저장소나 타 서비스를 건드리는 엔드포인트 | 경우에 따라 | 필요 | 옵션 |
| 데이터 상태 변경(남이 읽는 값을 쓴다) | 필요 | 필요 | **추천** |
| 스케줄러·배치·워커 | 필요 | 경우에 따라 | **추천** |
| 필드 추가·매핑·이름 변경 | 불필요 | 불필요 | **노출 안 함** |

필드 이름 바꾸는 데 TDD 는 엄밀함의 옷을 입은 간접비다. 마지막 행이 아예 노출하지 않는 이유다.

**TDD 인계.** TDD 를 골랐고 프로브가 `tdd` 스킬이나 rule 을 찾았으면 그것을 따르고 방법론을 여기서 재진술하지 않는다. 아무것도 못 찾았으면 재량으로 하되, 방법론이 가져갈 수 없는 불변식 셋은 지킨다:

- behavior 는 *public interface 를 통해 관찰*하지 내부 상태를 들여다보지 않는다
- 다음 behavior 는 직전 것이 통과한 뒤에만 시작한다
- **시도 예산은 behavior 가 아니라 항목에 속한다.** `min(15, 2a 에서 지목한 behavior 수 × 5)` 이고, 전략을 고를 때 고정된다. 이걸 상한으로 만드는 것은 평평한 15 다: 곱해지는 수를 상한 대상이 직접 고르는 곱은 상한이 아니다 — 검증 항목에 behavior 를 열둘 적으면 "behavior 당 5" 는 조용히 무인 시도 60회가 된다. behavior 당 상한만으로는 상한이 아니다 — behavior 개수를 정하는 것이 방법론이므로 16개면 80회를 사게 되고, 그중 무엇도 구현 루프 이터레이션이 아니다. 나중에 behavior 를 쪼개면 그 예산이 나뉠 뿐 늘지 않는다. 위임한 방법론은 *어떻게* 반복할지를 정하지 *얼마나 오래* 를 정하지 않는다

테스트 명령을 돌릴 수 없는 실행자에서는 TDD 가 불가능하다. 2c 에서 발견하지 말고 2a 에서 말한다.

## 2b · 구현

minimal-first, 이 순서로: 이미 있는 것 재사용 → 표준 라이브러리 → 플랫폼 → 의존성 → 한 줄 → 되는 최소.

재진입 시에는 직전 이터레이션의 실패·지적이 요구한 것**만** 구현한다. 이터레이션은 설계를 다시 열라는 초대가 아니다 — 그건 Step 1 에서 확정됐고, 여기서 다시 열면 두 예산을 모두 빠져나간다.

---

## 2c · 검증

명령을 이 순서로 해석하고, 어느 단을 썼는지 보고한다:

| 단 | 출처 |
|---|---|
| 1 | 프로젝트 config 의 `verify.command`, 다음 전역 config |
| 2 | repo 지문 (아래) |
| 3 | 1회 질문하고 답을 config 에 써서 다시 묻지 않는다 |

**프로젝트 config 에서 온 1단과 모든 2단 명령은 repo 와 함께 온 텍스트**이고, 이 루프는 그것을 이터레이션마다 실행한다. 해석된 명령을 출처와 함께 보이고 이 repo 에서 처음 돌기 전에 예스를 받는다 — 정확한 텍스트 단위로 1회, `P0-verify` 로 기록 (`SKILL.md` §런타임 레이아웃). 전역 config 의 1단과 3단은 사용자가 직접 친 것이고, 친 행위가 승인이었다.

| 지문 | 기본 명령 |
|---|---|
| `package.json` | `test` 스크립트, 없으면 `npm test` |
| `build.gradle` / `build.gradle.kts` | `./gradlew test` · Windows 는 `.\gradlew.bat test` |
| `pom.xml` | `mvn -q test` |
| `Cargo.toml` | `cargo test` |
| `pyproject.toml` / `setup.cfg` | `pytest` |
| `go.mod` | `go test ./...` |
| `test` 타깃이 있는 `Makefile` | `make test` |

**최초 검증은 공짜다.** 카운터는 *수리*를 제한하려고 있지, 사실을 알아내는 값을 물리려고 있는 게 아니다.

**환경 실패는 이터레이션이 아니고, 그 분류는 주장이 아니라 확인 대상이다.** 환경 실패로 치는 조건은 **같은 명령이 단위의 시작 커밋에서도 똑같이 실패할 때**뿐이다 — 거기서 돌려 보고 대조한다. 지금 트리를 옮기지 말고 일회용 worktree 에서 돌린다: `git worktree add --detach <단위 시작 커밋>` 로 만들어 돌리고 지운다(그 제거는 정리 규칙의 예외가 이미 덮는 경우다). 자리를 만들려고 checkout 하거나 stash 하면, 시험 대상인 구현을 `autonomy.md` §2 가 파괴적이라 부르는 그 작업들에 통과시키는 셈이다. 아니면 Redis 를 *추가하는* 항목이 내는 `ECONNREFUSED` 가 문자 그대로 "DB 미구동" 이 되어 무제한 무료 이터레이션을 사고, 명시된 탈출구("환경이 올라오면 다시 돌린다")는 영원히 오지 않는다 — 그 조건을 만든 것이 시험 대상인 변경이기 때문이다.

환경 판정이 연속 2회면, 둘 다 확인을 통과했더라도 멈추고 묻는다. 한 바퀴 뒤에도 안 올라온 환경은 이 루프가 고칠 것이 아니고, 예산을 안 쓰고 있다는 사실이 요점이 아니다 — 실행이 요점이다.

## 2d · 리뷰

**2c 가 통과한 뒤에만** 돈다. 도구는 프로브에서 고른다:

| 있는 것 | 쓸 것 |
|---|---|
| 리뷰 스킬·플러그인 | 실행 |
| 사용자가 직접 입력해야 하는 리뷰 명령 | 명령을 정확히 출력하고 대기 — 절대 대신 호출하지 않는다 |
| 아무것도 없음 | 단위의 변경 집합(`SKILL.md`)을 plan 과 대조해 직접 리뷰 |

세 번째 행은 폴백에 대한 변명이 아니라 진짜 리뷰다. Step 1 의 plan 이 명세이고, 의도와 구현을 대조하는 것이 바로 리뷰어가 하는 일이다. 그리고 여기가 집합 대신 트리를 읽으면 조용히 실패하는 자리다 — 그룹이 머지된 뒤 트리에는 읽을 것이 없고, 없는 것에 대한 리뷰는 아무것도 보고하지 않는다.

루프를 다시 여는 지적은 **결함과 계약 위반**이다. 스타일 취향과 "이러면 더 낫겠다" 는 이터레이션이 아니라 기록으로 간다 — 아니면 취향이 정확성용 예산을 먹는다.

```
검증   npm test — 34 passed, 0 failed        (2단, package.json)
리뷰   로컬 diff vs plan                      (리뷰 도구 없음)

  1  캐시 키에 정렬 파라미터가 빠졌다 — 정렬을 바꿔 요청해도 이전 순서가 반환된다
     → 결함, 루프 재개

  2  LRU 크기가 리터럴 500
     → 취향, 기록만
```

## 2e · 정리와 확정

정리는 **루프를 2회 이상 돈 경우에만** 나타난다. 한 번에 깨끗이 끝난 구현은 정리할 것이 없고, 그래도 단계를 띄우면 사람은 그 단계를 건너뛰는 법을 배운다.

범위는 **단위의 변경 집합**이다 — `SKILL.md` 가 한 번 정의하고 2d·2e·hard stop 검사·커밋이 전부 그 하나를 읽는다. 작업 트리가 아니다: dirty 한 트리에는 이전 단위의 파일이 섞여 있고, 머지된 그룹은 깨끗한 트리를 남긴다.

정리한 뒤 같은 예산에서 재검증 1회. 거기서 실패하면 다른 이터레이션과 똑같이 루프로 재진입한다. 예산이 이미 소진됐으면 **재검증 없이** 정리만 하거나 정리를 건너뛴다 — 정리하고 검증 없이 커밋하는 경로는 없다.

```
정리   2개 파일 정리 · 재검증 통과
확정   3/3 이터레이션 — 상한 도달, 미해결 지적 1건 (Phase 4 에 ⚠️ 로 기록)
```

지적이 남은 채 확정하는 것은 허용된다. 숨기는 것은 아니다 — Phase 4 요약에 지적 원문을 붙인 ⚠️ 행이 된다.
