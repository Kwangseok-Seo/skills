<what-to-do>

작업 목록을 받아 각 항목을 고정된 사이클로 커밋까지 몰고 간다:
**설계 루프 → 구현 루프(구현 / 검증 / 리뷰) → 커밋.**

"그냥 작업하기" 와 다른 점은 둘이다.

1. **자율성 다이얼.** 모든 결정 지점은 위험 등급을 갖는다. 무인 실행은 *레벨이 허용* **∧** *등급이 auto-eligible* 일 때만 — 둘 중 하나로는 안 된다. 네 부류의 행위는 `auto` 를 포함한 모든 레벨에서 사람에게 묻는다.
2. **append-only 결정 로그.** 추천 하나, 선택 하나, 나중의 결과 하나가 각각 한 줄로 append 된다. 이 로그가 다이얼을 올릴 근거다 — 다이얼은 감으로 올리지 않는다.

고정 순서: **셋업(1회) → 프로브 → 작업 해석 → 정렬 → 그룹핑 → 항목별 사이클 → 요약.**

아래 게이트가 계약이다 — 진입 조건·상한·금지선. 선택지 문안·판단표·절차 등 나머지는 `references/` 에 있고 **그 경로에 진입할 때 1회만 on-demand 로 읽는다.**

**이 스킬은 커밋에서 멈춘다.** push·PR 생성·머지·회고는 하지 않는다. 그건 이미 쓰고 있는 다른 스킬에 넘긴다.

**`git` 이 필요하고, git 저장소도 필요하다.** 나머지는 전부 강등하고 그 사실을 말하지만, git 이 없으면 단위 기준선도 변경 집합도 worktree 도 커밋도 없다 — 실행 자체가 없다.

</what-to-do>

## 런타임 레이아웃

```
~/.claude/task-routine/config.json                      # 전역 config (위저드가 쓴다)
<repo>/.claude/task-routine.json                        # 프로젝트 override (선택)
~/.claude/task-routine/<project-slug>/decisions.jsonl   # append-only 결정 로그
~/.claude/task-routine/<project-slug>/run-<id>.json     # 체크포인트
```

상태를 **repo 밖**에 두는 건 의도다 — 파일을 스테이징하는 무인 실행이 자기 로그를 커밋할 수 있으면 안 된다. `TASK_ROUTINE_DIR` 로 루트를 바꾼다.

**config 는 키 단위로 프로젝트가 전역을 덮지만, 두 파일의 신뢰도는 같지 않다.** 프로젝트 config 는 *repo 와 함께 도착한* 파일이다. 그러니 프로젝트에 관한 사실 — `source`, `verify.command`, 관행 — 은 적을 수 있어도 **얼마나 무인으로 도는지**는 적을 수 없다: `autonomy.*` · `auto.*` · 루프 상한은 전역 config 아니면 명령줄에서만 온다. 그 선을 넘은 프로젝트 키는 무시하고 무시했다고 한 줄 남긴다. 나중에 스키마에 추가되는 키도 누군가 분류하기 전까지는 프로젝트 config 에서 무시된다. 조용한 우선순위가 바로 클론한 repo 가 다이얼을 `auto` 로, 항목 상한을 50 으로 세팅하게 만드는 길이다.

**repo 가 준 명령은 여기서 처음 돌기 전에 승인받는다.** 프로젝트 config 의 `verify.command`, 그리고 repo 파일에서 끌어낸 명령(`package.json` 의 `test` 스크립트, `Makefile` 타깃)은 둘 다 이 머신이 쓰지 않은 텍스트다. 해석된 명령을 출처와 함께 보이고 예스를 받은 뒤에만 돌린다 — repo 당 한 번, 정확한 텍스트 단위로. 그래서 명령을 고치면 다시 묻는다. **그 프롬프트만이, 오직 그것만이 `P0-verify` 로 기록된다.** 사용자가 직접 친 명령(위저드, 또는 3단)은 친 행위가 곧 승인이라 프롬프트도 없고 레코드도 쓰지 않는다. `P0-verify` 줄이 존재하는 이유는 나중 실행이 "이 repo 가 준 텍스트가 여기서 승인됐나" 를 묻기 위해서인데(`references/telemetry.md`), 물은 적도 없는 명령에 그 줄을 쓰면 아무도 던지지 않은 질문에 답하는 것이고, 조회에 걸리려면 `mode: "asked"` 를 주장해야 하는데 그것은 그냥 거짓이다. 자격증명처럼 생긴 것을 담은 config 는 승인이 아니라 실행 중단이다 (`references/setup.md`).

유효 설정은 값마다 출처를 달아 **Phase 1 이 무엇을 하기 전에** 출력한다. 자기 실행의 자율성 레벨을 요약에서 처음 아는 사람은 그것을 승인한 적이 없는 사람이다.

## 인자

- `setup` — 위저드를 돌리고 종료. config 가 없어서 **자동으로** 발동한 경우엔 종료하지 않고 그 호출이 실행으로 이어진다.
- `report` — 결정 로그 성적표를 출력하고 종료. 로그를 읽기만 하고 아무것도 바꾸지 않으며 다이얼을 건드리지 않는다.
- `--source=<ref>` — 이번 실행의 작업 소스(파일 경로, GitHub 이슈 번호/URL, 어댑터별 ref). 기본은 config.
- `--todos=1,3` — 지정 항목만 처리. 정렬·그룹핑은 건너뛴다.
- `--level=manual|assisted|auto` — 이번 실행의 다이얼 override.
- `--auto` — `--level=auto` 단축. **저장하지 않는다.** 무인은 항상 명시적 선택이다.
- `--resume` — 최신 체크포인트를 읽어 status 가 `pending` 인 첫 단위부터 이어간다. `pending` 단위가 **하나도 없는데** 쥐고 있는 완료가 남은 체크포인트는 Phase 4 의 일괄 반영으로 재진입한다: Phase 1–3 과 항목별 사이클을 건너뛰고, 그 반영에 필요한 것은 여기 고정한 목록이 아니라 필요한 대로 읽는다. 체크포인트가 이미 커밋을 담고 있는 `pending` 단위는 구현 루프가 아니라 Step 3 의 완료 표시부터 재개한다 — 그래서 체크포인트를 단위 시작·종료에 더해 **커밋 직후에도** 쓴다(`references/telemetry.md`). 다이얼은 거기서 물려받지 **않는다**: 무인 재개에는 `--auto` 를 다시 붙여야 한다. 체크포인트의 `source_ref` 와 다른 `--source` 는 두 실행의 병합이 아니라 정지다.

인자 없이 config 가 있으면 설정된 소스에서 작업을 해석한다.

## 능력 프로브 (매 실행 1회)

저장된 목록을 믿지 말고 실물에 묻는다 — 스냅샷은 사용자가 뭔가를 깔거나 지운 순간 썩는다.

프로브 대상: 외부 CLI(`git`, `gh`, 그리고 설정된 실행자 `codex`/`herdr` 등)를 `command -v` / `Get-Command` 로, 설치된 스킬·에이전트를 `~/.claude/skills/`·`~/.claude/agents/`·`~/.claude/plugins/installed_plugins.json`·프로젝트 `.claude/` 에서. `git worktree` 는 항상 있으므로 프로브 불요. 서브에이전트가 실행자 계약을 만족하는지는 이 목록이 아니라 그 계약이 답할 질문이다(`references/execution.md`).

config 스냅샷과 다르면 **한 줄로 알리고 갱신한다.** 능력 상실은 절대 조용히 넘어가지 않는다 — "병렬 불가, 순차로 진행" 은 보고이지 생략이 아니다.

## 자율성: 레벨 × 등급

```
무인 실행  ⟺  레벨이 이 단계를 허용  ∧  등급 == auto-eligible  ∧  hard stop 신호 없음
```

| 레벨 | 동작 |
|---|---|
| `manual` | 모든 결정을 묻는다. 손으로 사이클을 도는 것과 동일. |
| `assisted` *(기본)* | **추천이 붙은** auto-eligible 결정만 무인. 나머지는 묻는다. |
| `auto` | auto-eligible 결정 전부 무인. 추천이 없는 자리는 근거를 한 줄 적고 진행. |

**등급이 지정되지 않은 결정은 `manual-only` 로 취급한다.** 모르면 묻는다 — 가드는 열린 쪽이 아니라 닫힌 쪽으로 실패한다.

## Hard stop — `auto` 포함 모든 레벨에서 묻는다

1. `H1` **밖으로 나가는 행위** — `push`, PR 생성·머지, 태그 푸시, 릴리스 발행.
2. `H2` **파괴적 로컬 작업** — 두 시험, 어느 하나면 충분: 복구 불가한 바이트, **또는** plan 이 지목한 적 없음.
3. `H3` **외부 트래커 쓰기** — 코멘트, 상태·체크박스, 라벨·담당자.
4. `H4` **security 표면 접촉** — 5신호 중 하나면 충분.

이들이 모든 레벨에서 발동하므로 **`references/autonomy.md` 는 매 실행, Phase 1 이전에 읽는다.** 각 부류의 시험이 거기 있다. 레벨이 정하는 것은 어느 *결정*을 묻느냐이지, 어느 *행위*를 지키느냐가 아니다.

**입력을 얻을 수 없는 시험은 정지다 — 깨진 입력의 목록이 아니라 규칙으로 쓴다.** 입력이 없으면 통과도 없다. 고장 났을 때 조용해지는 가드는 없는 것만 못하다.

## 무인 실행의 브레이크

| 브레이크 | 기본값 | 발동 시 |
|---|---|---|
| 시작 시 dirty 트리 | 아래의 경로 목록들 | 미커밋 내역을 나열하고 기준선으로 기록 (아래) |
| 커밋이 단위의 집합 밖에 닿음 | 아래 집합 | 멈추고 질문 — `--auto` 만이 아니라 모든 레벨에서 |
| 1회 실행당 항목 수 | 5 (`auto.max_tasks`) | 진행 보고 후 계속할지 질의 — **남은 항목이 있을 때만** |
| 연속 단위 실패 | 2 | 루프 전체 중단 — 연속 실패는 시도가 아니라 전제가 틀렸다는 신호 |
| 항목당 설계 검토 라운드 | 3 | 질의: 1회 더 / 현 설계로 확정 / 이 항목 SKIP / 중단 |
| 항목당 검토자 호출 총합 | 라운드 + 1 (4) | 질의: 1회 더 / 현 설계로 확정 / 이 항목 SKIP / 중단 |
| 단위당 구현 루프 이터레이션 | 3 | 질의: 1회 더 / 현 상태로 확정 / 이 항목 SKIP / 중단 |
| 항목당 TDD 시도 | `min(15, 2a 에서 지목한 behavior 수 × 5)` | 질의: 재시도 / SKIP / 재설계 / TDD 해제 / 중단 |

**각 카운터는 자기가 제한하는 것의 경계에서 리셋되고, 그 경계는 서로 다르다:**

| 카운터 | 제한 대상 | 리셋 시점 |
|---|---|---|
| 설계 라운드 · 검토자 호출 · TDD 시도 | 항목 하나 | 다음 항목이 시작할 때 |
| 구현 루프 이터레이션 | **단위** 하나 — 순차 항목, 또는 예산·검증·리뷰를 하나씩 공유하는 머지된 병렬 그룹 | 다음 단위가 시작할 때 |
| 연속 실패 | **실행 전체**, 단 **항목** 단위로 센다 | 항목이 ✅ 로 끝났을 때만 |

연속 실패 카운터를 지우는 것은 ✅ 뿐이다. ⚠️ 와 ⏭️ 는 올리고, 머지된 그룹은 담은 항목 수만큼 올리며, **항목이 시도됨으로 치는 시점은 이 실행이 그 항목의 예산 중 하나를 처음 쓴 순간이다** — Step 1 의 첫 리뷰어 디스패치, 또는 Step 2 의 첫 편집, 둘 중 먼저 온 쪽. Step 2 진입에만 걸어 두면 라운드 3회와 리뷰어 4회를 쓰고 설계 상한에서 버려진 항목이 *시도된 적 없음*으로 적히고, 코드가 생기기도 전에 전부 미수렴하는 체크리스트는 이 브레이크를 아예 못 건드린다. **`❓` 는 둘 다 하지 않는다** — 사이클은 끝났으니 진행 실패가 아니고, 실행이 뒷받침할 수 없는 것이 나왔으니 깨끗한 성공도 아니다. 이걸 올리게 두면 실행의 정지 시점이 그룹핑 결정의 손에 넘어간다: 5항목 그룹의 미달 1건이 단위 하나에 대한 관측 1건으로 5를 만든다. 설계·구현·TDD 예산은 서로 독립이고, 환경 실패(DB 미구동, 서비스 부재)는 이터레이션을 소비하지 않는다.

**어느 종료 상태가 무엇을 올리는지, 스코프를 왜 그 자리에 그었는지, 여섯 항목 추적표: `references/autonomy.md`.** 리셋 경계를 잘못 잡는 것이 상한을 도달 불가로 만드는 경로이므로, 여기서 재구성하지 말고 거기서 읽는다.

## "이 단위가 바꾼 것" 의 정의 — 하나의 집합을 모두가 읽는다

단위는 시작할 때 기준선을 기록한다: **시작한 커밋, 그리고 그 시점에 트리에서 이미 dirty 였던 경로들.**

```
변경분 = git diff <단위 시작 커밋>          # 트리 vs 그 커밋 — 머지된 커밋과
         (먼저 git add -N, 그래야 새 파일이   # 미커밋 편집이 둘 다 들어온다
          안 보이지 않는다)
       − 단위 시작 시점에 이미 dirty 였던 경로
```

2d 의 리뷰, 2e 의 정리 범위, 모든 hard stop 검사, 커밋이 스테이징하는 것 — 전부 **그 하나의 집합**을 읽는다. 맨 `git diff` 도, 워킹 트리 전체도 아니다: 병렬 그룹이 머지된 뒤 트리는 깨끗하고 작업물은 커밋 안에 있으므로, 트리를 읽는 검사는 아무것도 못 찾고 **없음으로 통과**한다.

**뺄셈의 양쪽은 같은 명령쌍이 내는 맨 경로 목록이다** — 추적되는 변경은 `git diff --name-only -z --no-renames <커밋>`, untracked 는 `git ls-files --others --exclude-standard -z`. 그래야 바이트로 비교할 수 있다. `--no-renames` 는 장식이 아니다: 감지가 켜져 있으면 `git mv old new` 가 `new` 하나만 내고 `old` 의 삭제는 집합에 못 들어와, 2c 를 통과한 트리에는 하나뿐이던 파일이 커밋에는 둘 다 실린다. 반대쪽에 `git status --porcelain` 을 쓰지 않는다: 상태 문자 2개와 공백을 앞에 붙이고, rename 을 NUL 필드 2개로 쓰되 접두사는 첫 필드에만 붙이며, untracked 디렉터리를 통째로 `dir/` 로 접는다. 그걸 diff 에서 빼면 **한 건도 안 맞아**, 뺄셈이 막으려던 경로가 전부 커밋에 실린다. untracked 쪽은 `git add -N` **이전에** 뜬다 — 안 그러면 집합이 그 파일들을 잃어서가 아니라, 그 목록이 **이 실행의 intent-to-add 항목을 사용자의 것과 갈라 주는** 유일한 것이기 때문이다. 실측: `add -N` 이후 `ls-files --others` 는 새 파일을 더 이상 내지 않지만 `git diff --name-only` 가 그것을 내기 시작해 합집합은 어느 순서로 읽어도 같다 — 그리고 `git status --short` 는 intent-to-add 항목을 이 실행이 만든 것이든 사용자가 만든 것이든 똑같이 ` A` 로 찍는다. git 은 목록은 줄 수 있어도 **그중 어느 절반이 되돌릴 내 것인지**는 못 준다. 먼저 읽으면 준다.

되돌리는 시점은 **Step 3 이 끝난 뒤 — 커밋됐든 아니든**이지, 집합을 계산한 직후가 아니다. 일찍 되돌리면 git 이 아직 모르는 경로에 대해 `git commit --only` 가 커밋 전체를 거부한다 — 실측: `error: pathspec 'fresh.txt' did not match any file(s) known to git`, exit 1, 커밋 없음 — 그래서 파일을 새로 만드는 단위는 전부 그 자리에서 실패한다. 반대로 커밋이 일어나지 않았다고 되돌리지 않으면, 사용자의 다음 `git commit -a` 가 이 실행이 건드린 새 파일을 전부 실어 보낸다.

**그리고 이 실행이 인덱스에 넣는 것은 `add -N` 만이 아니다.** 쓰기 작업 자신이 스테이징할 수 있다 — `git mv` 는 옛 경로의 삭제를, `git rm` 은 제거를 스테이징한다 — 그리고 `--only` 는 그것들을 빼고 커밋할 뿐 치우지 않으므로 그대로 남는다. 실측: 한 단위가 dirty 경로 정지를 지나친 뒤 `git mv` 가 만든 스테이징된 삭제가 이후 두 단위 내내 인덱스에 앉아 있었고 실행이 끝날 때까지 남아 있었다 — 요약에 안 보이고, 사용자의 다음 맨 `git commit` 을 기다리면서. **이 실행이** 스테이징했는데 커밋이 가져가지 않은 것을 `add -N` 되돌리기와 같은 시점에 unstage 하고 — `git restore --staged <경로>`, 실측으로 스테이징된 `D ` 를 미스테이징 ` D` 로 바꾸고 작업 트리는 건드리지 않는다 — 나머지는 발견한 그대로 둔다 — 남이 스테이징한 작업은 남의 것이다. `--resume` 에서는 어느 항목이 이 실행 것인지에 대한 기록이 없으므로 아무것도 unstage 하지 않고, 그렇게 남긴 경로를 요약이 말한다.

**이 집합은 경로 목록이고, 내용이 필요한 검사는 그 집합으로 *제한한* diff 를 읽는다.** 2d 의 리뷰와 `references/autonomy.md` 의 ⓑ hunk 검사는 추가된 줄·삭제된 줄·주변 문맥이 필요한데 `--name-only` 에는 그것이 없다. 집합은 *어느 경로가 이 단위의 것인가*를 말하고, hunk 를 읽어야 하는 검사는 `git diff <단위 시작 커밋> -- <집합>` 으로 트리 전체를 읽지 않고 그것을 얻는다.

- **plan 이 파일을 지목한 단위인데 집합이 비었으면 그것은 정지**이지 통과가 아니다 — 검사를 못 돌린 경우와 같은 규칙이다.
- 커밋은 정확히 그 집합만 스테이징한다. 대칭으로: 집합 **밖**의 것은 남의 무관한 작업이고, 집합 **안**인데 plan 이 지목한 적 없는 것은 계획 밖 과잉이다 — 어느 쪽이든 말하고 커밋 전에 묻는다. 포매터가 60개 파일을 다시 쓴 경우가 두 번째이고, 여집합만 심문하는 가드는 그것을 영원히 못 본다. **이 단위가 H2 의 scope 시험에서 이미 사용자에게 내놓은 경로는 여기서 다시 묻지 않는다** — 이미 승인됐다고 이름을 대고 커밋은 진행한다. 한 경로, 한 질문: H2 프롬프트가 그 경로를 보여 준 이유가 *plan 이 지목한 적 없어서*이고 그것은 이 시험이 올릴 사실과 같다. 답 하나에 두 번 묻는 것은 생성기를 부르는 항목이 있는 실행마다 프롬프트를 두 배로 만든다. 반대는 성립하지 않고, 그래서 이 시험은 남는다: 계획 밖 과잉은 어떤 쓰기 작업도 알린 적 없는 경로까지 덮고, 그것은 H2 가 보여 줄 기회조차 없던 것이다. **이 시험은 경로를 읽지 줄을 읽지 않는다** — 지목된 파일 *안*에서 plan 이 승인한 적 없는 변경은 이걸 통과하고, 그것을 덮는 것은 2d 가 diff 를 plan 에 대고 리뷰하는 자리다. 줄 단위로 만들려 들지 않는다: "plan 이 이 줄을 승인했나" 는 일반해가 없고 헛정지만 산다.
- **쓰기 작업은 두 번, 서로 다른 질문으로 읽힌다.** 각 작업 *전에* H2 는 그것이 무엇을 없애려 하는지 묻고, 그 읽기는 요청된 작업 자체에서 온다 — 바이트가 사라진 뒤의 정지는 보고이기 때문이다(`references/autonomy.md`). 각 작업이 끝나면 그 경로들이 **이 단위가 쓴 것의 기록**으로 쌓이고, Step 3 의 주장 검사가 마지막에 읽는 것이 그것이다. 머지된 그룹의 기록은 워커들이 돌려준 변경 파일 목록의 합집합이다(`references/execution.md`) — 그 쓰기를 메인 스레드가 한 것이 아니기 때문이다.
- **파괴 여부 시험은 이 집합이 아니라 이 단위가 *쓴* 경로를 읽는다.** `git diff` 는 ignored 파일을 보여줄 수 없고 뺄셈이 untracked 파일을 지우므로, H2 를 변경 집합으로 태우면 정확히 그것이 지켜야 할 파일들에 눈이 먼다. 그 경로는 쓰기 작업 자체에서 가져온다.
- **시작 시점에 이미 dirty 였던 경로를 이 단위가 써야 한다면 멈추고 묻는다 — 그리고 작업이 내용을 *옮기거나 복사*할 때는, 그 내용을 가져오는 쪽 경로도 놓는 쪽 경로와 똑같이 시험한다.** 위의 뺄셈은 남의 미커밋 작업을 이 커밋에서 빼 주는데, *이 단위 자신의* 그 경로 쓰기도 똑같이 뺀다 — 그대로 진행하면 그 파일 없이 커밋하고 아무 말도 안 하게 된다. 해악은 누락 — 또는 작업이 내용을 옮기는 경우, 이 단위 것이 아니었던 작업의 흡수 — 이고, 어느 쪽이든 단위의 **작업**에 관한 것이지 혼동에 관한 것이 아니다. 놓이는 쪽만 보면 뺄셈 자신의 전제가 무방비로 남는다: 뺄셈은 경로에 걸려 있어서 내용이 제자리에 있는 동안에만 성립한다. 실측 — `old.txt` 가 dirty 인 상태에서 `git mv old.txt new.txt` 는 남의 미커밋 줄을 `new.txt` 로 실어 갔고, `new.txt` 는 단위 시작 시점에 깨끗해 아무것도 빼지 않았으며, `old.txt` 의 삭제는 *빠졌다*. 커밋은 남의 작업을 실어 보냈고 검증된 트리가 지웠던 파일을 그대로 남겼는데, 아무것도 묻지 않았다. 같은 이동을 *프로그램*이 하는 경우는 한 층 앞에서, 그 자신의 근거로 멈춘다: 목적지가 애초에 명령 텍스트에 없다(`references/autonomy.md`). 진행은 허용되지만 조용한 진행은 아니다 — **그 경로들에서 커밋이 무엇을 틀리게 하는지를 이름으로 말한다**, 그 단위의 행과 요약에, 그리고 양방향으로: 뺄셈이 이 단위 자신의 쓰기를 지운 쪽은 *누락*, 이동이 dirty 경로의 내용을 깨끗한 경로로 옮겨 뺄셈이 막을 것이 없던 쪽은 *추가*. 누락만 나열하는 보고는 놓이는 쪽 사례만 설명하고, 남의 줄을 이 항목의 메시지로 실어 보낸 절반에 대해서는 침묵한다. **진행한 단위는 ✅ 가 아니라 ❓ 로 끝난다.** 루프는 수렴했으므로 이것은 진행 실패가 아니고 브레이크를 올려서도 안 된다 — 단위 하나에 대한 관측 1건이 머지된 그룹에서는 항목 수만큼 세어질 것이고, 그것은 미달된 테스트 주장을 카운트에서 빼 두는 것과 같은 산수다. 그렇다고 깨끗한 성공도 아니다: 그 경로들에서 커밋은 이 실행의 어떤 검증도 본 적 없는 상태를 기록하고, 그것이 바로 `unverified` 가 이미 뜻하는 바다.
  - **Step 3 의 완료 표시는 이 정지가 관할하지 않는 유일한 쓰기다.** 애초에 커밋에 들어가면 안 되는 유일한 쓰기이기 때문이다: 커밋 뒤에 만들어지므로 어떤 변경 집합도 담을 수 없고, 집합에서 빠져도 잃는 게 없다. 이게 없으면 앞선 모든 단위 — 그리고 앞선 모든 실행 — 이 남긴 표시가 다음 단위의 시작 시점에 dirty 로 잡혀, 실행은 첫 항목에서 영원히 멈춘다. 면제의 근거는 **그 쓰기가 순서상 어디에 놓이는가**이므로 `--resume` 에서도 내일의 재호출에서도 성립한다. "이 실행이 쓴 경로" 라는 기억은 둘 중 어디에서도 살아남지 못한다.
- `--resume` 에서 트리는 구조상 dirty 다. 재개된 단위가 같은 방식으로 자기 기준선을 기록하므로, 재개에는 위 규칙 어디에도 예외가 필요 없다.

## Phase 1–3 — 작업 해석 · 정렬 · 그룹핑

소스에서 작업 목록을 가져와 의존성으로 정렬하고, 병렬 가능한 것을 묶은 뒤 실행자를 고른다.

출력 형태와 판단 예시: **[PHASE-FORMAT.md](./PHASE-FORMAT.md)**. **한 그룹이라도 항목을 2개 이상 담으면** `references/execution.md` 를 읽는다 — 공유 repo 에 동시 워커를 넣는 조건이 그것이고, *그룹 수*로 세면 6항목짜리 그룹 1개에서는 침묵하고 1항목짜리 그룹 6개에서는 발동한다. 항목이 2개 미만이면 그룹핑을 통째로 건너뛰고 순차 사이클로 간다.

**해석과 정렬 사이에서 각 항목의 변경 표면을 예측한다.** 정렬도 그룹핑도 파일에 대한 판단인데, Step 1 이 내놓는 파일 목록은 둘 다에 쓰기엔 너무 늦다. 이건 설계가 아니라 스캔이다: 항목 텍스트를 읽고, 명백한 소유 파일을 repo 에서 검색하고, 항목당 경로 한 줄을 적는다. 범위를 묶는다 — 항목당 검색 1회, 검색이 돌려준 것 이상은 읽지 않기, 아무것도 못 찾으면 추측하지 말고 경로를 `?` 로 남기기. **`?` 인 항목은 순차로 정렬한다** — 모르는 것으로부터 서로소를 증명할 수는 없다.

| Phase | 결정 | 등급 | 접히지 않는 조건 |
|---|---|---|---|
| 1 해석 | `P1-source` | auto-eligible | **목록이 없으면 실행도 없다** — 어디를 찾아봤는지 말하고 멈춘다. 작업을 지어내지 않는다 |
| 2 정렬 | `P2-order` | auto-eligible | `--todos` 가 있으면 통째로 건너뛴다 |
| 3 그룹핑 | `P3-exec` | auto-eligible | 병렬 worker 는 **쓰기 권한 필수** — read-only 로 뜨면 편집이 거부되는데도 성공을 보고한다 · 검증·리뷰·커밋은 언제나 **머지 이후** 그룹 단위 순차 |

## 항목별 사이클

루프 둘과 커밋 하나. 각 항목은 `TASK [n/N]: <제목>` 배너로 시작한다.

**Step 1 · 설계 — 내부 루프.** 틀린 설계는 코드가 생기기 전에 잡는 게 가장 싸다. 이 루프가 없으면 처음 검사하는 자리가 Step 2d, 완성된 코드 위다.

`1a 자료수집 → 1b 설계 → 1c 독립 검토 → 1d 반영 → (1c 로, 최대 3) → 1e 확정`

검토자 선정 · 브리프 구성 · 판정 어휘 · skip 판정표: **[DESIGN-LOOP.md](./DESIGN-LOOP.md)**.

- **검토자는 설계자가 아니고, plan 을 받되 추론은 받지 않는다.** 설계 대화를 넘기면 돌아오는 것은 검토가 아니라 동의다.
- **지적의 수용·기각은 이 스레드가 한다.** 검토자는 조언하지 결정하지 않는다 — 아니면 Phase 4 감사 표가 내가 하지 않은 선택을 내 것으로 적는다.
- **루프를 건너뛴다** — 단일 파일이고 새 인터페이스·스키마·의존성이 없으면, **그리고 그 표면이 이번 실행에서 이미 검토됐으면**: 다시 검토하지 말고 확정된 plan 을 확장한다. 이 둘째 조항이 없으면, 한 기능을 조각낸 체크리스트가 같은 설계를 조각마다 한 번씩 검토하게 되고 매번 다른 조각을 못 보는 검토자가 본다. 이것만 믿고 건너뛰지는 않는다: 전체 판정표는 `DESIGN-LOOP.md` 에 있고, 항목 텍스트를 security 신호에 대고 읽은 결과가 코드 이전에 루프를 강제할 수 있다.
- **건너뛴 루프도 plan 은 확정한다** — 정렬 전 범위 스캔이 만든 한 줄짜리 파일 목록이 그것이다. 건너뜀은 "검토가 필요 없었다" 이지 "plan 이 없다" 가 아니다: 파괴 여부의 범위 시험이 묻는 것이 *plan 이 무엇을 지목했나* 이고, plan 이 없으면 그 답은 *비교할 것이 없음* 이 되어 통과로 읽힌다.
- **라운드로 세지 않는 판정도 호출은 소비한다.** `NEEDS_MORE_INFO` 는 라운드 카운터에서만 면제되지, 항목당 `라운드 + 1` 발송이라는 천장에서는 면제되지 않는다. 쓸 수 없는 판정이 연속 2회면 멈추고 묻는다.
- 결정 `S1-design`, 등급 `auto-eligible`.

**Step 2 · 구현 — 루프.** 구현·검증·리뷰는 예산 하나를 공유하는 한 루프다. 그래서 정리 단계의 노출 조건이 플래그 두 개가 아니라 **루프 상태**가 된다.

`2a 전략 → 2b 구현 → 2c 검증 → 2d 리뷰 → (실패·지적이면 2b 로, 예산 3) → 2e 정리·확정`

검증 명령 감지 · 리뷰 도구 · 정리 범위 · TDD 인계: **[BUILD-LOOP.md](./BUILD-LOOP.md)**.

- 결정 `S2-test`(2a, **한 번만** — 루프는 2b 로 재진입)와 `S2-review`(2d), 등급 `auto-eligible`. TDD 를 고르면 **방법론은 위임하되 상한은 위임하지 않는다** — 상한은 여기 남는다.
- **구현은 minimal-first**, 만들기 전에 재사용한다. **검증·보안·접근성·하위호환은 깎지 않는다.**
- **리뷰는 검증이 통과한 뒤에만 돈다.** 그래서 실패한 이터레이션은 리뷰 비용을 안 쓰고, 재리뷰 상한이 따로 없다.
- **최초 검증 1회는 카운트하지 않고**, 환경 실패도 언제나 카운트하지 않는다.
- **정리는 이터레이션이 아니라 출구에 속하며**, 루프를 2회 이상 돈 경우에만 나타난다.
- 사용자가 직접 입력해야 하는 리뷰 도구는 **요청만 하고 호출하지 않는다** — 그렇게 말하고 기다린다.

**Step 3 · 커밋과 완료 표시.** 커밋 메시지 컨벤션은 repo 에서 끌어온다(`git log --pretty=%s`, 최근 ~20건). 안 잡힐 때만 `<type>: <summary>` 폴백, 소스가 참조를 주면 포함한다.
- 결정 `S3-commit`, 등급 `auto-eligible`. 단위의 변경 집합만 커밋하고 그 밖은 담지 않는다 — **`git commit --only -- <집합>`**. 인덱스가 그것만 담고 있다고 믿을 수 없기 때문이다: 집합의 정의가 요구하는 `git add -N` 이 남이 미커밋으로 둔 *삭제*를 **스테이징된** 삭제로 승격시키고, 맨 `git commit` 은 그것을 이 항목의 메시지로 실어 보낸다. `--only` 는 인덱스가 *이미* 들고 있던 것을 무시한다. 하지만 샌드박스는 **아니다**: 훅에게 임시 인덱스를 넘기므로 `lint-staged` 류의 pre-commit 훅이 스테이징하면 그대로 커밋에 들어온다 — 실측으로, `git add b.txt` 를 하는 훅이 남의 미커밋 줄을 담은 `b.txt` 를 `git commit --only -- a.txt` 안으로 밀어 넣었다. 그러니 커밋을 되읽어 집합 **밖**의 것이 있으면 멈춘다: `git show --format= --name-only -z --no-renames <방금 만든 커밋>`. 이 옵션들은 하나도 장식이 아니다 — 맨 `git show --name-only` 는 커밋 헤더를 앞에 찍고, `-z` 가 없으면 git 이 비ASCII 경로를 `"caf\303\251.txt"` 로 내놓아 어떤 바이트 비교도 살아남지 못하며, rename 감지를 켠 채로 두면 `git mv` 가 새 경로 하나만 내서 2경로 집합과 1경로 커밋이 어긋난다 — 정확히 맞는 커밋인데도. **검사 방향은 그 하나뿐이다**: 머지된 그룹의 집합은 워커 커밋이 이미 실어 보낸 경로를 정당하게 담고 있고 `--only` 는 그것들에 대해 아무것도 커밋하지 않아 되읽기에서 빠진다 — 실측으로 exit 0, 2경로 집합에서 1경로만 커밋됐다. 이 되읽기는 집합 위의 다른 모든 것처럼 이름을 읽으므로, 이미 집합에 있는 파일을 훅이 *다시 쓴* 경우는 이름이 늘지 않아 여기를 통과한다 — 그리고 그것을 잡는 것은 다른 데도 없다. 2d 는 커밋 전에 돌았고 훅은 커밋 안에서 돌기 때문이다. 이 되읽기가 그 구멍을 닫는다고 가정하기보다 한계로 알아 두는 편이 낫다. 그리고 이 되읽기는 게이트가 아니라 보고다: 커밋이 존재한 뒤에 돌므로 무엇도 예방하지 못하고, 늘어난 경로를 이름으로 대며 실행을 멈출 뿐이다 — 커밋이 로컬이고 가역이기에 감당 가능한 것이고, 그것이 잡는 스테이징이 애초에 정지감인 이유는 그러지 않으면 다음 단위가 남의 미커밋 작업을 흡수한 커밋에서 기준선을 뜨기 때문이다. 빈 집합은 커밋이 아니다: 경로 없는 `--only` 는 exit 128 이고, 수리가 필요 없던 병합 그룹은 여기서 커밋할 것이 정당하게 없다 — 그 경우 `--only` 는 128 이 아니라 `nothing to commit` 과 함께 exit **1** 을 낸다. 0 이 아닌 종료 코드를 전부 커밋 실패로 읽는 실행은 잘된 그룹에 실패를 기록하고 그것으로 브레이크를 올린다. 아주 큰 집합은 OS 인자 한계를 넘는다 — 실측으로 1,200 경로 커밋이 `Argument list too long` 으로 실패한다 — 그러니 `--pathspec-from-file=- --pathspec-file-nul` 로 넘긴다. 집합이 이미 만들어져 있는 NUL 구분 형태 그대로 받는 것이고, 근거는 집합의 양쪽을 `-z` 로 뜨는 것과 같다. 커밋은 로컬이고 가역이다. push 는 아니고, push 는 hard stop 이다.
- **머지된 그룹의 항목별 커밋은 머지 전에 worker 브랜치에서 만든 커밋이다**(`references/execution.md`). 그러니 이 단계가 덮는 것은 머지 이후 루프가 스스로 바꾼 것뿐이고, 수리가 필요 없던 그룹에서는 그것이 아무것도 아니다.
- **단위를 자기 테스트 주장에 대고 검사한다.** `S2-test` 가 이 단위를 무엇이 검증할지 지목했고, **이 단위가 쓴 경로** — H2 가 이미 쓰기 작업에서 가져오는 그 목록 — 이 무엇을 냈는지 말한다. `none` 이 아닌 전략인데 **테스트 경로를 하나도 추가·변경하지 않았다면** 주장 미달이다. 작업은 그대로 커밋한다 — 게이트가 아니라 보고다 — 그리고 단위는 ✅ 대신 **`❓`** 로 끝난다. 통과한 스위트는 대체물이 못 된다: 이 단위가 검사됐든 아니든 통과하며, 단위의 변경 전체를 지워도 모든 테스트가 초록으로 돌아오는 것으로 측정된다.
  - **변경 집합이 아니라 쓴 경로**를 읽는다. 집합에는 dirty 경로 뺄셈이 이미 적용돼 있어서, 시작 시점에 dirty 였던 경로에 단위가 진짜로 쓴 테스트가 거기서는 *쓰지 않은 테스트*로 읽힌다. **기록은 어디에 썼는지만이 아니라 무엇을 했는지 — 추가·수정·삭제 — 를 담는다.** 추가와 수정만 센다. 맨 경로 목록으로는 그걸 표현할 수 없고, 그러면 `rm tests/cache.test.ts` 가 테스트 경로를 기록에 넣어 방금 다시 쓴 코드의 테스트를 지우는 것이 이 검사를 만족시키는 가장 싼 방법이 된다. 같은 이유로 기록은 단위의 **끝**에서 읽는다: 한 이터레이션에서 쓰고 다음에서 지운 테스트는 이 단위가 낸 테스트가 아니다.
  - **무엇이 테스트 경로인지는 파일명 패턴 목록이 아니라 repo 에서 읽는다** — 이 repo 가 이미 테스트를 두는 자리, 픽스처와 골든 파일 자리를 포함해서, 모노repo 라면 이 변경이 닿는 부분에서. **테스트가 별도 경로가 아님이 실제로 확인되는 repo** — 이 repo 소스에서 `#[cfg(test)]` 블록이나 in-source Vitest 가드를 실제로 찾은 경우 — 에서는 여기서 읽을 것이 없다: Phase 1 에서 한 번 말하고 그 repo 에서는 이 검사를 돌리지 않는다. **아직 테스트가 없는 repo 는 그 경우가 아니고** 해당하지 않는다: 거기서 테스트를 주장한 단위는 첫 테스트를 써야 하고, 그게 바로 이 검사가 있는 이유다. 모든 단위에 `❓` 를 찍는 것은 정직함이 아니라, 의미 있는 행을 파묻는 잡음이다.
  - **`none` 은 반대 방향으로 검사한다.** 테스트가 필요 없다고 주장해 놓고 그 근거로 든 행이 덮을 수 없는 것을 썼으면 — "문서" 로 `none` 을 정당화했는데 기록에 소스 파일이 있으면 — 반대편에서 같은 주장 미달이고, 다른 것과 똑같이 `❓` 이자 `unmet` 이지 `unclaimed` 가 아니다. 이게 없으면 이 검사를 통과하는 가장 싼 길은 코드가 생기기도 전인 2a 에서 아무것도 주장하지 않는 것이 된다.
  - **상한에 닿았고 주장도 미달인 단위는 `❓` 가 아니라 ⚠️ 다.** 칸은 하나이고 상태 칸은 브레이크가 읽는 값을 싣는다. 미달 사실은 그 행의 줄에 적는다 — 예산이 떨어진 단위야말로 테스트를 안 썼을 가능성이 가장 높으므로, 그 줄을 잃어서는 안 되는 마지막 행이다. `❓` 는 예산 안에서 사이클을 끝낸 단위의 것이다.
  - **머지된 그룹의 항목들은 각자 자기 `S2-test` 를 worker 를 띄우기 전에 고르고, 그룹은 그래도 판정 하나로 끝나 모든 항목 행에 찍힌다.** 미리 고르는 이유: 머지 뒤에 고르는 전략은 워커들의 테스트가(또는 그 부재가) 이미 보이는 상태에서 고르는 것이고, 답을 보고 나서 한 주장은 어떤 단위도 못 어긴다(`references/execution.md`). 판정이 하나인 이유: 쓴 것을 다시 갈라낼 수 없기 때문이다 — worker 는 각자 자기 변경 파일 목록을 돌려주지만 머지 이후 루프의 수리는 그룹의 것이지 그 안 어느 항목의 것도 아니어서, 항목별 판정은 쓴 것의 한쪽 절반엔 맞고 다른 절반엔 자의적이 된다. 그래서 읽는 것은 합집합이다 — 어느 항목이든 테스트를 주장했으면 그룹이 쓴 것에 테스트 경로가 있어야 하고, 모든 항목이 `none` 을 주장했으면 반대 방향 검사가 그룹 전체에 적용된다. 양방향으로 거칠다: 어딘가의 테스트 경로 하나가 전원의 주장을 충족시키고, 미달 1건이 전원을 표시하는 것과 대칭이다. **일부는 테스트를 주장하고 일부는 `none` 을 주장한 그룹은 앞 검사만 받는다** — 반대 방향 검사는 *이* 단위가 안 하겠다던 동작을 실었는지를 묻는 것인데, 공유된 쓰기 목록 안의 한 항목에 그것을 물을 방법이 없다. 그룹이 양쪽에서 검사된다고 가정하기보다 한계로 알아 두는 편이 낫다.
  - **이것이 세워 주지 않는 것**: 그 테스트들이 이 변경을 실제로 검사한다는 것. 새 코드를 import 만 하고 아무것도 단언하지 않는 테스트 파일도 이걸 만족시킨다. 그 틈을 닫으려면 코드가 없는 상태에 대고 테스트를 돌려야 하고, 그건 다른 도구이며 이 스킬에 없다. 여기서 그것을 덮는 것은 2d 가 diff 를 plan 에 대고 리뷰하는 자리다.
- 이어서 **소스에** 완료를 표시하되 등급은 단계가 아니라 **소스가 정한다**: 로컬은 즉시 반영, 원격은 `pending` 으로 쥐다가 Phase 4 에서 일괄(`references/sources.md`). 이게 없으면 `--resume` 이 이미 커밋한 일을 다시 한다.

## Phase 4 — 요약

항목별 결과 표를 출력하고 실행을 마감한다. 컬럼 정의와 감사 표 레이아웃: **[PHASE-FORMAT.md](./PHASE-FORMAT.md)**.

- **⚠️ 와 ❓ 행은 수동 확인 대상** — 상한에 닿았는데도 진행했거나, 이 실행이 뒷받침할 수 없는 것을 단위가 커밋한 케이스다: 전략이 주장한 테스트가 없거나, dirty 경로 정지를 지나쳐 커밋이 2c 가 검증한 트리와 다르거나.
- **완전 수동 실행이 아니었다면 결정 감사 표는 필수다**: 사용자 대신 무엇을 골랐는지, 왜, 결과가 그 선택을 뒷받침했는지. 무인 모드가 허용되는 유일한 이유가 사후 감사이므로, 이 표를 빼면 허용의 근거 자체가 사라진다.
- 결정마다 `outcome` 한 줄을 append 한다(`references/telemetry.md`). `manual_intervention` 은 **정직하게** — 개입 없이 깔끔하게 성공한 것만 다이얼을 올릴 근거가 된다.
- 한 단계가 두 근거 문턱을 새로 넘었으면 **한 줄로 말하고 거기서 멈춘다.** 실행의 부수효과로 다이얼을 올리지 않는다.
- **pending 완료는 한 번에 몰아 반영한다.** 원격 소스의 완료는 Step 3 이후 쥐고 있었다: 전부 보이고 **실행당 1회** 묻는다, 항목마다가 아니라. 거부되거나 실패한 쓰기는 `pending` 으로 남기고 절대 완료로 보고하지 않는다.
- **로컬 소스의 완료 표시가 어디 있는지 말한다.** 표시는 자기가 속한 커밋 *뒤에* 쓰이므로 이 실행의 어떤 커밋에도 들어 있지 않다 — 파일명과 개수를 적고(`TODO.md — 완료 표시 4건, 미커밋`) 사용자가 자기 메시지로 커밋하게 남긴다. 침묵은 "커밋됨" 으로 읽힌다.
- **두 번 실패했거나 거절된 일괄 반영에는 출구가 필요하다.** 읽기 전용 소스는 영원히 *실패*하지 *거절*되지 않으므로 거절만으로 걸면 그 실행엔 출구가 없다. 두 번째에 선택지를 준다: 반영 / 다음으로 보류 / 이 완료들을 버리고 쓰지 않았다고 말하기. 세 번째가 없으면 체크포인트는 영원히 닫히지 않고 이후의 모든 `--resume` 이 같은 프롬프트를 다시 연다.
- **실행이 끝났고 동시에 pending 이 없을 때만 마감한다** — 체크포인트 파일 자체는 남긴다. 다음 실행이 그 정렬·그룹핑을 직전 분석으로 읽기 때문이다(`references/telemetry.md`).

## 중단과 재개

"중단" 응답이나 브레이크 발동 시 체크포인트를 쓰고 출력한다: 끝난 것, 남은 것, 그리고 `--resume` 으로 이어간다는 안내. 재개는 카운터와 결정 이력을 복원하므로 상한이 세션을 넘어 살아남는다.

**작업 소스가 진실의 원천이다.** 단 하나의 예외는 트래커 쓰기가 `pending` 인 완료 항목. 그 외 체크포인트의 카운터·결정 이력은 장부일 뿐이고, 둘이 어긋나면 소스가 이긴다.

## Never

- ❌ push·PR·머지·파일 삭제·트래커 쓰기를 묻지 않고 실행 — 어느 레벨에서도
- ❌ hard stop 판정이 실패한 것을 통과로 처리
- ❌ 등급이 불명인 결정을 "봐도 괜찮으니까" 무인 실행
- ❌ 병렬 → 순차, 설정 도구 → 기본값으로 강등하면서 말하지 않기
- ❌ 검토자에게 설계 대화를 넘겨놓고 독립 검토라고 부르기
- ❌ 설계가 이미 깨끗하게 돌아왔는데 남은 검토 라운드를 소진하기
- ❌ 프로브 대신 능력 목록을 config 에 복제
- ❌ 결정 로그의 기존 줄을 고치기 — 결과는 append 이지 in-place 병합이 아니다
- ❌ 이번 실행 경로가 진입하지 않는 `references/` 파일 적재
