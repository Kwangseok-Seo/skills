# DESIGN-LOOP — Step 1 의 검토 프로토콜

> 루프를 켠 채 Step 1 에 진입할 때 1회 읽는다. **게이트** — plan 만 넘김, 누가 결정하나, 언제 건너뛰나 — 는 `SKILL.md` 에 있다. 이 파일은 프로토콜과 출력 형태다.

```
1a 자료수집 → 1b 설계 → 1c 독립 검토 → 1d 반영 → (1c 로, 최대 3) → 1e 확정
```

이 파일을 관통하는 예시는 `PHASE-FORMAT.md` 실행의 항목 3 — */admin/\* 에 관리자 role 요구*.

---

## 1a · 자료수집

plan 을 쓰기 전에 두 출처를 읽는다. 하나만 읽으면 실패 양상이 정해져 있다:

| 출처 | 답하는 것 | 이것만 읽으면 |
|---|---|---|
| **바닥** — 코드가 지금 하는 것 | 관행, 기존 이음매, 재사용할 수 있는 것 | legacy 를 그 실수까지 충실히 재생산 |
| **천장** — 성숙한 레퍼런스 구현이 하는 것 | 관용구, 남들이 이미 밟은 실패 | 안착할 코드베이스와 싸우는 설계 |

legacy 의 **표면**은 맞춘다 — 명명, 파일 배치, 에러 형태 — diff 가 이 저장소 것처럼 읽히도록. legacy 의 **논리**는 맞추지 않는다. 둘이 갈라지는 자리가 의도적 일탈이고, 그건 아래처럼 적어 두지 얼버무리지 않는다.

넓은 탐색은 검색 에이전트에 위임하되 읽는 것은 직접 한다. 열어보지 않은 파일의 요약은 근거가 아니다.

---

## 1b · 설계

plan 은 이 순서로 진술한다: 무엇이 바뀌는가, 어디가, 그리고 무엇을 건드리지 않는가. 로컬 관행에서 의도적으로 벗어나면 정확히 세 줄을 붙인다:

```
일탈    핸들러마다 검사하는 대신 guard 미들웨어
  문제  /admin/* 아래 핸들러 12개가 각자 role 검사를 재구현
  푸는것 role 모델이 바뀔 때 고칠 자리가 하나 · 새 핸들러는 기본으로 커버
  비용  미들웨어 순서가 기능을 떠받치게 된다 — 나중에 순서를 바꾸면 조용히 무력화
```

값을 하는 것은 세 번째 줄이다. 비용이 안 적힌 일탈은 아직 생각이 끝나지 않은 것이다.

---

## 1c · 독립 검토

### 검토자 선정

가능한 가장 높은 단이 이기고, **어느 단에 내려앉았는지 말한다**:

| 단 | 요건 | 독립성 |
|---|---|---|
| 다른 벤더의 CLI | 프로브가 찾았고 비대화형 실행 가능 | 다른 모델·다른 학습·다른 프롬프트 계보 |
| 다른 모델의 서브에이전트 | 항상 가능 | 다른 모델, 같은 계보 |
| 같은 모델의 새 에이전트 | 항상 가능 | 컨텍스트 격리만 |

3단도 진짜 검사다 — 새 컨텍스트는 실제로 뭔가를 잡아낸다 — 하지만 셋 중 가장 약하고, 어느 단을 썼는지 빠진 보고는 그 단서를 주장으로 바꾼다.

1단의 세부는 설정된 도구 쪽에 속한다. 이 스킬이 요구하는 것은 셋뿐이다: 브리프를 stdin 이나 파일 인자로 받을 것, 비대화형으로 돌 것, 아래 네 판정 중 하나를 돌려줄 것. **셋을 다 못 하는 도구는 1단이 아니다** — 2단으로 내려가고, 다른 강등과 똑같이 그 사실을 보고한다.

### 브리프

넣는다:

- 작업 진술과 수용 기준
- plan, 그대로
- 그것이 인용한 출처 — 파일 경로와 각각이 보여준 것
- 2라운드 이상이면: 지난 라운드 이후 무엇이 바뀌었는지, 반영한 지적당 한 줄

빼낸다:

- 설계 대화 — 요약한 형태라도
- 세 줄 일탈 노트를 넘어서는 설계자의 추론
- 지난 라운드 지적에 대한 나 자신의 평가

**이 제외 목록이 이 단계 전체의 요점이다.** 설계자의 논증을 받아 든 검토자는 그것을 재생산하고 승인을 돌려준다 — 그 승인은 검토가 없는 것보다 나쁘다, 뒷받침처럼 읽히기 때문이다. 브리프에 넣을지 말지 애매하면 빼라. 맥락을 더 달라는 검토자는 작동하고 있는 검토자다.

### 판정

| 판정 | 뜻 |
|---|---|
| `APPROVE` | 만들어라 |
| `APPROVE_WITH_CHANGES` | blocking 을 고친 뒤 만들어라 |
| `REJECT` | 디테일이 아니라 접근 자체가 틀렸다 |
| `NEEDS_MORE_INFO` | 브리프가 부족했다 — 요청받은 것을 채워 재실행한다. 라운드 카운터는 안 올라가고, 호출 카운터는 올라간다 |

지적은 둘로 나뉘며, 나누는 것은 검토자가 한다:

- **blocking** — 이것 없이는 plan 이 틀렸거나 불완전하다
- **non-blocking** — 개선, 취향, 후속

```
검토 — 항목 3 · 2단(서브에이전트, 다른 모델) · 라운드 1
APPROVE_WITH_CHANGES

blocking
  1  미들웨어가 라우트 테이블 뒤에 등록돼 /admin/health 가 guard 보다 먼저 잡힌다.
     plan 의 순서 노트가 "이르게" 라고만 하고 어디인지 못박지 않았다.

non-blocking
  2  문자열 비교 대신 타입 있는 Role enum 검토
  3  순서 속성을 이름으로 가진 테스트가 없다 — 조용히 회귀한다
```

## 1d · 반영

blocking 을 고친다. 나머지는 plan 의 `deferred` 아래에 한 줄 이유와 함께 기록한다 — 기록은 동의가 아니고, 다음 라운드에서 다시 다투지 않는다.

`NEEDS_MORE_INFO` 는 라운드가 아니다. 요청받은 것을 채워 라운드 카운터를 올리지 않고 재실행한다 — 그래야 검토자가 질문만으로 설계 예산을 소진시키지 못한다.

**그래도 호출은 호출이고, 호출에는 별도의 천장이 있다.** 브리프를 검토자에게 보낸 모든 발송을 센다 — 라운드로 세는 판정, 세지 않는 판정, 도구 실패 후의 재시도까지 무엇이 돌아오든 — 그리고 항목당 총합을 `design_loop.rounds + 1`(기본 4)로 제한한다. 어떤 판정을 라운드에서 면제하면서 아무 데서도 세지 않는 것이 바로 그 면제를 무제한 예산으로 만드는 길이다: 브리프는 일부러 맥락을 빼고, 재실행마다 *다른* 질문을 하는 새 검토자가 붙고, 라운드 카운터는 0 을 벗어나지 않는다.

연속 2회는 천장보다 먼저 멈춘다. 쓸 수 있는 판정 없이 돌아온 발송이 연달아 둘 — `NEEDS_MORE_INFO` 재발 또는 파싱 불가 — 이면 브리프와 검토자가 수렴하지 않는다는 뜻이고, 세 번째가 그걸 고치지 않는다. 두 질문을 모두 보고하고 묻는다: 답을 채움 / 현 plan 확정 / 이 항목 SKIP / 중단.

---

## 1e · 확정

**첫** clean 판정에서 나온다 — `APPROVE` 또는 blocking 0. 라운드는 천장이지 할당량이 아니다. 이미 깨끗한 설계에 3라운드째를 쓰는 것은 서브에이전트 하나를 쓰고 아무것도 사지 않는 일이다.

blocking 을 전부 반영한 `APPROVE_WITH_CHANGES` **가** 그 clean 판정이고, 1c 로 돌아가지 않고 여기서 나온다. 그 판정의 정의 자체가 "고친 뒤 만들어라" 이고, 고친 것이 고쳐졌다는 답을 들으러 돌아가는 것은 아무도 의심하지 않은 답에 호출 하나를 쓰는 일이다. 반영한 수정은 확정 기록에 이름을 적어 남긴다. 루프를 다시 여는 예외는 하나 — blocking 수정이 **표면 자체**를 옮길 때(새 public 메서드, 스키마 변경, 새 의존성). 뒤 항목이 그 표면을 확장할 때 루프를 다시 여는 것과 같은 이유다.

```
검토 — 항목 3 · 2단 · 라운드 2
APPROVE
  순서를 app.use() 가 router 앞에 오도록 못박음 · 속성 테스트를 plan 에 추가

설계 확정 — 3라운드 중 2라운드.
```

**라운드** 상한에서는 질의한다: 1회 더 / 현 설계 확정 / 이 항목 SKIP / 중단. **호출 천장**에서는 선택지가 *현 설계 확정 / 이 항목 SKIP / 중단* 이다 — "1회 더" 는 없다. 천장은 바깥 경계이고, 자기를 옮기겠다고 제안하는 바깥 경계는 경계가 아니라 권고다. 다음 발송은 그 천장을 다시 밟아 또 묻게 되고, 결국 정의상 보고 있지 않은 사람의 인내심만이 유일한 한계가 된다. blocking 이 남은 채 확정하는 것도 허용되며, 그때는 Phase 4 요약에 ⚠️ 행으로 반드시 실려야 한다.

## 언제 루프를 건너뛰나

되돌리기 비싼 것을 만들면 돌리고, 국소하고 자명하면 건너뛴다.

| 건너뜀 | 돌림 |
|---|---|
| 단일 파일, 새 인터페이스 없음 | 공개 인터페이스 신설·변경 |
| 이름 변경, 필드 추가, 문구 수정 | 스키마·데이터 포맷·전송 포맷 |
| 설정값 변경 | 새 의존성 |
| 이미 테스트가 덮고 있는 동작 | 새 보안·권한 표면 — 아직 diff 가 없으므로 **항목 텍스트**를 ⓑ 어휘에 대고 읽는다 |
| — | 모듈을 가로지르는 3파일 이상 |

**이번 실행에서 이미 검토된 표면은 루프를 다시 트리거하지 않는다.** 체크리스트는 대개 한 기능을 조각낸 것이라 그중 넷쯤이 같은 새 모듈을 건드린다 — 그 설계를 조각마다 한 번씩 검토하면 답 하나를 네 번 사는 것이고, 게다가 각 검토자는 다른 조각을 못 본 채 파편만 보므로 넷 다 *"통합 시나리오가 없다"* 를 지적한다. 정작 그건 다음 항목이 채운다. 확정된 plan 을 확장하고, 확장했음을 기록한다:

```
설계    항목 1 에서 확정된 plan 을 확장 (표면: src/cache/*)
        추가: 무효화 훅 · 재검토 없음
```

확장이 **표면 자체를 바꿀 때만** 루프를 다시 연다 — 그 인터페이스의 새 public 메서드, 스키마 변경, 새 의존성. 한 시간 전에 검토한 인터페이스에 호출자를 하나 더 붙이는 것은 설계 결정이 아니다.

`--auto` 에서는 이 산수가 중요하다 — 루프는 항목당 최대 서브에이전트 3개이고, 거기에 항목 상한이 곱해진다. 건너뛴 루프도 돌린 루프와 똑같이 이유와 함께 보고한다.
